**Architecture and code review — 17 October 2026 (Malaysia time)**

**Verdict: retain the architecture; do not approve a general production rollout of this working tree.** FastAPI, a confined LangGraph coordinator, psycopg async transactions, PostgreSQL queues, an outbox, and an independently authorized console are a sensible foundation for this product. The release blockers are authorization and lifecycle defects, plus an unverified deployment path. Changing frameworks or adding more agents would not resolve them.

The current implementation is suitable for continued isolated development with synthetic fixtures. Customer-triggered KB administration, credential-bearing logs, unauthenticated marketplace account binding, shadow/mute bypasses, and unverified callback replies must be corrected before real-tenant use. Findings about the shipped production Compose file describe that file; they do not establish how any separately configured live server behaves.

The reviewed tree was based on Git revision `018becd`, with substantial existing tracked and untracked changes, including migration 0290 and the private sandbox. This review includes those changes. Application code, dependency manifests, migrations, environment files, and running services were left unchanged. The review adds this document only; executable probes and their logs are under `/tmp`.

**Scope and method.** I inventoried 130 runtime Python files (18,231 lines), 262 application SQL files, 19 SQL migrations, 68 Python test/support files, and 33 JSON golden cases. I inspected the architecture, progress/handoff documents, relevant LG phase requirements, core runtime and persistence paths, identity/console authorization, adopted frontend, build/deployment definitions, and evaluation harness. This was a repository-wide structural review with detailed inspection of security and recovery boundaries, supported by executable probes. It is not a claim that every line of the copied, inactive PM/legacy frontend was audited. Inert reference components and future LG14 functionality are not implemented production features.

All database probes used new disposable Docker PostgreSQL containers and generated fixtures. HTTP probes used ASGI or mock transports. No production database, bot token, n8n instance, or live provider was used, and no environment-file contents were read.

Useful patterns already present include transaction-local tenant scope, a path-safe parameterized query loader, sorted stock locks and duplicate-SKU aggregation, contact-bound order confirmations, execution-time capability-switch rechecks, durable file publication/deletion fencing, and bounded password hashing off the event loop. These are concrete implementation strengths to carry into the weaker boundaries identified below.

**Findings are ordered by priority.** P1 means fix before production rollout or enabling the affected integration. P2 means a concrete correctness or operational defect that needs an explicit resolution or feature restriction. A reproduction that confirms a defect is a successful diagnostic, not a passing safety requirement.

1. **P1 — A customer plan can administer the tenant knowledge base.** [Planner wiring](/home/amsyrzmi/CSAV2/csa/turn/deps.py:95) exposes the complete `KbInput` schema. [Task validation](/home/amsyrzmi/CSAV2/csa/decide/llm.py:222) blocks only the two order button actions; [the runner](/home/amsyrzmi/CSAV2/csa/agents/runner.py:107) restricts KB operations only for `web`. [KB handlers](/home/amsyrzmi/CSAV2/csa/agents/kb/agent.py:68) accept ingest, delete, list_gaps and resolve_gap without a staff principal. With KB enabled, a Telegram customer therefore has a path to poison/delete shared knowledge and inspect other customers' gap queries. A disposable-Postgres probe admitted model-shaped tasks and actually ingested and deleted a synthetic document through the real runner and capability registry without staff context. Enforce an operation allowlist derived from a trusted principal at execution time, expose only customer-safe schemas to the planner, and retain staff authorization inside administrative services. RLS protects tenant boundaries; it does not distinguish customer and staff operations within a tenant.

2. **P1 — HTTP request logging exposes credentials embedded in URLs.** [Logging configuration](/home/amsyrzmi/CSAV2/csa/core/logging.py:192) sends stdlib INFO logs to the output sink without secret sanitization. [Telegram transport](/home/amsyrzmi/CSAV2/csa/channels/telegram.py:177) places the bot credential in the URL, which HTTPX includes in its INFO request log. A mock-transport probe confirmed that a synthetic bot credential reached the configured log output. [OAuth token exchange](/home/amsyrzmi/CSAV2/csa/channels/marketplace/oauth.py:102) also places sensitive parameters in a URL and exposes HTTP exception text in logs/errors. Suppress credential-bearing library request logs and sanitize structured events, exception chains, URLs and query parameters before output. Use safe error codes at public boundaries. This is a demonstrated logging path, not evidence that a production secret has already leaked.

3. **P1 — Marketplace OAuth lets an unauthenticated caller choose the tenant receiving credentials.** [Authorize](/home/amsyrzmi/CSAV2/csa/channels/marketplace/router.py:124) accepts `client_id` and signs state without a human session, administrator role or tenant permission. [Callback](/home/amsyrzmi/CSAV2/csa/channels/marketplace/router.py:157) trusts that signed tenant and persists credentials. The gateway mounts these routes independently of console identity. An ASGI reproduction obtained state and reached the mocked credential-save operation for a chosen synthetic tenant with no cookies. Require an authorized tenant administrator at initiation, persist a one-use transaction tied to that session and tenant, and validate the binding before saving tokens. Allow only configured redirect destinations and escape provider-controlled values in the HTML response. Signing caller-selected data does not supply authorization. [OAuth Security BCP](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.7.1) also requires suitable transaction/user-agent binding for CSRF protection.

4. **P1 — Shadow authority is inconsistent and fail-safe replies bypass it.** [The normal gate](/home/amsyrzmi/CSAV2/csa/graph/policy/gate.py:58) suppresses shadow output, but [fail_safe](/home/amsyrzmi/CSAV2/csa/turn/deps.py:484) unconditionally writes an outbound message and delivery, with no policy read. A disposable-Postgres probe set the client policy to shadow, invoked the failure path and verified the persisted fallback. A provider failure during shadow evaluation can therefore produce an extra customer reply alongside the incumbent runtime. Normal-path authority can also disagree: [ingress configuration](/home/amsyrzmi/CSAV2/db/sql/ingress/get_channel_credentials.sql:1) falls back to `clients.deployment_mode`, while [graph policy loading](/home/amsyrzmi/CSAV2/db/sql/turn/get_client_policy.sql:1) reads only `config.policy` and otherwise defaults to auto. A legacy column-only shadow setting therefore does not suppress graph replies. Apply one deployment/mute authority to every execution and customer-egress path, including errors and deadlines. Also prevent shadow evaluation from making business changes: agent execution precedes the reply gate, and draft creation can reserve stock even if the eventual reply is suppressed. A final reply gate is not an execution authorization gate.

5. **P1 — All callback turns bypass grounding, including model-written replies.** [Verification](/home/amsyrzmi/CSAV2/csa/turn/deps.py:335) returns true for any callback. The narrow verbatim path in [compose](/home/amsyrzmi/CSAV2/csa/turn/deps.py:313) covers only successful order confirm/cancel with the relevant setting enabled; other callbacks can use the model. [Gate policy](/home/amsyrzmi/CSAV2/csa/graph/policy/gate.py:61) then treats every callback as a system reply, ahead of suggest/never_auto checks. A probe supplied an unsupported model-written refund claim: normal deterministic grounding rejected it, while callback verification accepted it and suggest-mode gating returned send. Exempt only code-selected, deterministic acknowledgements with explicit provenance. Model-generated callback text must undergo the usual verification and applicable review policy.

6. **P1 — Human ownership is not consistently respected.** [Context SQL](/home/amsyrzmi/CSAV2/db/sql/turn/get_conversation_state.sql:1) recognizes only a non-null future `ai_muted_until`; it does not recognize `owned_by='human_support'` with a null expiry, which LG04 defines as indefinite human ownership. A real-DB probe confirmed this state loads as `human_muted=false`. Separately, [the graph](/home/amsyrzmi/CSAV2/csa/graph/coordinator.py:465) calls signals before routing the muted turn; a classifier error enters fail_safe and sends a fallback. The latter also reproduced with an in-memory graph. Derive mute state from the authoritative ownership/expiry contract, short-circuit before model work, and make the error/egress boundary honor muting too. Scheduler tests preserving indefinite ownership do not prove that conversation processing respects it.

7. **P1 — The shipped queue role makes workers silently idle.** [Compose](/home/amsyrzmi/CSAV2/deploy/compose.yml:36) supplies `csa_app` for `LG_DATABASE_URL`. [Worker startup](/home/amsyrzmi/CSAV2/apps/worker/main.py:470) and delivery startup use that URL for their cross-tenant queue pools. [Claim SQL](/home/amsyrzmi/CSAV2/db/sql/worker/claim_ingress.sql:1) runs without setting the tenant GUC, while the queue tables have tenant RLS. A disposable-Postgres probe showed `IngressWorker(app_pool, app_pool)` returned no work with a pending event; an owner-backed test claim processed it. The similarly configured delivery worker also saw no pending delivery. Define a narrow dispatch role or carefully scoped claim functions, and test the exact deployed grants. Do not solve this by disabling RLS or putting broad owner credentials into all services. PostgreSQL's documented [RLS evaluation](https://www.postgresql.org/docs/16/ddl-rowsecurity.html) explains why the unscoped application-role query sees no eligible rows.

8. **P1 — The application Dockerfile omits required project metadata.** [The build stage](/home/amsyrzmi/CSAV2/deploy/Dockerfile:18) copies `pyproject.toml`, `uv.lock` and source directories, but never copies the README declared by [project metadata](/home/amsyrzmi/CSAV2/pyproject.toml:5). An offline wheel build in a temporary directory reproducing that metadata/source boundary failed with `Readme file does not exist: README.md`. This was a metadata/build-boundary reproduction, not a full image build. Copy the required metadata and add a clean application-image build to CI; tests running from a complete checkout cannot catch this omission.

9. **P1 — The production Compose file does not supply a viable runtime configuration.** [Secret mounts and environment](/home/amsyrzmi/CSAV2/deploy/compose.yml:36) use lowercase secret filenames, while [Settings](/home/amsyrzmi/CSAV2/csa/core/settings.py:44) is case-sensitive and requires uppercase field names. A temporary-secret-directory probe left `GROQ_API_KEY` and `CREDENTIALS_KEY` missing despite the lowercase Compose-style files being present. Compose also does not pass required `PUBLIC_BASE_URL`. After startup issues are fixed, it still leaves `TURN_ENGINE` at its [echo default](/home/amsyrzmi/CSAV2/csa/core/settings.py:111). Explicitly configure secret targets, required settings and the intended engine, then boot all three processes against disposable Postgres and verify a synthetic turn. Optional console/KB settings and storage also need an explicit deployment profile before those features are offered.

10. **P2 — A deadline after emit can produce both a normal reply and a fallback.** [Finalize](/home/amsyrzmi/CSAV2/csa/graph/coordinator.py:421) deliberately raises to avoid sending a fallback after an emitted reply. However, [the outer timeout handler](/home/amsyrzmi/CSAV2/csa/graph/coordinator.py:543) always calls fail_safe. A synthetic graph emitted normally, blocked in finalize, and then invoked a fallback on deadline. The normal and fallback paths use different message keys, so normal outbox deduplication does not collapse them. Make completion/fallback selection transactional and aware of an already-persisted customer outcome. Test deadlines before, during and after emit, as well as the resume path.

11. **P2 — Ticket mutations do not all have durable operation idempotency.** [Adding a note](/home/amsyrzmi/CSAV2/csa/agents/tickets/agent.py:263) appends an event without consulting the context key. A real-DB probe executed the same input with the same key twice and observed two note events. [Ticket creation](/home/amsyrzmi/CSAV2/csa/agents/tickets/agent.py:185) uses a ten-minute subject/time duplicate check rather than an operation receipt; this cannot cover an arbitrarily delayed checkpoint retry. Store a unique operation key and payload digest with each mutation/result in the same transaction. A graph checkpoint and a non-empty context key alone do not make the underlying side effect idempotent.

12. **P2 — KB extraction silently drops valid source content.** [Long-word splitting](/home/amsyrzmi/CSAV2/csa/agents/kb/chunking.py:22) slices oversized words without retaining the remainder. A 1,201-character unbroken Chinese string produced only 600 characters, losing 601. [CSV FAQ extraction](/home/amsyrzmi/CSAV2/csa/agents/kb/extract.py:240) also truncates an entire Q/A pair at `max_chars * 4`; a synthetic 3,000-character answer yielded a 2,400-character combined chunk. Preserve all text through bounded successive chunks, retain question/context on answer continuations, or explicitly reject unsupported sizes. Add content-preservation invariants alongside size tests; bounded chunks can still be incomplete chunks.

13. **P2 — DLQ redrive does not match the payload written by the worker.** [Worker failure recording](/home/amsyrzmi/CSAV2/apps/worker/main.py:330) stores the raw wrapper in `dlq.envelope`. [Redrive](/home/amsyrzmi/CSAV2/csa/ops/runbooks.py:60) treats that wrapper as a flat Envelope, seeks an endpoint in nonexistent `meta.endpoint_id`, substitutes tenant UUIDs for missing routing IDs, wraps it again and creates a queue trace without rebinding the embedded trace. Actual payloads therefore fail routing/contract checks or foreign keys. [The current test](/home/amsyrzmi/CSAV2/tests/test_cutover_ops.py:411) seeds a different hand-written shape and does not run the worker on the result. Recover from the original ingress identity, preserve operation idempotency, validate a typed redrive contract, and mark replay status atomically with a valid enqueue. Exercise failure → DLQ → redrive → completed turn end to end. Delivery-stage replay also needs an implemented recovery path.

14. **P2 — The new runtime does not maintain usable multi-turn context.** [Context loading](/home/amsyrzmi/CSAV2/csa/turn/deps.py:160) loads the existing summary and active-order IDs, but no recent message content. [Finalization SQL](/home/amsyrzmi/CSAV2/db/sql/turn/update_conversation_turn.sql:1) never updates the summary, and no runtime summarizer writes it. [Planner context](/home/amsyrzmi/CSAV2/csa/decide/llm.py:110) receives only the summary, a boolean about orders and first-contact status. For conversations created by this runtime, a clarification such as "Which SKU?" followed by "the blue one" has no reliable prior-turn content available to resolve the answer. Trace-ID checkpoints are per-turn recovery state, not conversation memory. Load a bounded redacted history and/or maintain an explicit typed dialogue state/summary with a token budget. Keep tenant/contact scoping on every context source.

15. **P2 — The invoice agent advertises download links to an unimplemented route and hides configuration failures.** [The agent](/home/amsyrzmi/CSAV2/csa/agents/invoices/agent.py:185) catches every settings exception, switches to a public fixed development signing value/localhost URL, and still returns success. It also falls back to the credential-encryption key when a signing key is absent. It emits `/api/v1/invoices/{id}/download`, for which no active download handler exists; [the console](/home/amsyrzmi/CSAV2/csa/console/router.py:409) correctly returns 501 for the deferred artifact feature. Disable the customer `download_link` action until artifact delivery exists. Require a dedicated signing secret and surface missing configuration when that feature is implemented. Do not describe a fabricated or unreachable URL as a secure available download.

16. **P2 — Outbox claims do not preserve conversation delivery order.** [Delivery claim](/home/amsyrzmi/CSAV2/db/sql/delivery/claim.sql:1) selects any due row and skips locked rows, without excluding later messages whose earlier conversation delivery is pending/delivering. A retry delayed by backoff allows a later reply to overtake it even with one delivery process; replicas add another overtaking path. If ordered replies are required, enforce the predecessor constraint and conversation serialization/fencing in the delivery layer. The ingress worker's conversation lock does not protect a different process's outbound transport.

17. **P2 — Composer and Telegram text limits are inconsistent.** [Composition](/home/amsyrzmi/CSAV2/csa/decide/llm.py:372) admits up to 8,000 characters. [Transport](/home/amsyrzmi/CSAV2/csa/channels/telegram.py:164) forwards the entire text without channel validation or splitting. Telegram documents a [4,096-character sendMessage limit](https://core.telegram.org/bots/api#sendmessage). Long accepted drafts can therefore enter retries/DLQ instead of reaching the customer. Enforce channel limits before persisting the final outcome, or use a deterministic, ordered multi-message representation with stable sequence keys and intentional button placement.

18. **P2 — Health checks do not match the process work model.** [The heartbeat loop](/home/amsyrzmi/CSAV2/csa/core/liveness.py:58) touches the file before awaiting the full work item. [Compose](/home/amsyrzmi/CSAV2/deploy/compose.yml:88) requires freshness within ten seconds, while legitimate turns can take ninety seconds and individual delivery requests can reach their configured read deadline. This can report healthy work as unhealthy. The gateway health command also invokes `curl`, which the runtime Dockerfile does not install, and uses liveness rather than readiness. Use a concurrent event-loop heartbeat plus a separate work-progress/lease signal, and ship a probe executable that actually exists in the image. Verify these checks with deliberately slow synthetic turns.

19. **P2 — Accepted marketplace events have no compatible consumer, and dormant adapter paths still need validation.** [Marketplace ingress](/home/amsyrzmi/CSAV2/csa/channels/marketplace/ingress.py:131) enqueues a raw channel/payload object. [Worker parsing](/home/amsyrzmi/CSAV2/apps/worker/main.py:444) requires `raw.envelope`, and turn dispatch supports only Telegram and web. Consequently, enabling the webhook can acknowledge an event which the worker then fails repeatedly and dead-letters. Keep this integration unavailable until it has a typed event contract and a matching consumer. Default commerce adapters are unwired, as the console catalogue correctly states. Before future activation, add contact ownership checks and operation authorization for merchant-wide reads/inventory/fulfillment. Also validate provider application-status envelopes: a mock HTTP 200 carrying a vendor rejection became a fabricated `UNPAID`/zero-amount order in [get_order](/home/amsyrzmi/CSAV2/csa/agents/ecommerce/adapters/tiktok_shop.py:80); fulfillment returned false, which [the agent](/home/amsyrzmi/CSAV2/csa/agents/ecommerce/agent.py:197) ignored before reporting success. This probe demonstrates dormant code behavior, not a live marketplace result.

Several secondary operational concerns merit follow-up: the role-password step occurs after migration 0100 is stamped in a separate transaction, so a failed provisioning step is skipped on an ordinary rerun; database circuit-reset helpers do not reset a running process's in-memory breaker; and the manual approval-expiry SQL changes status/audit without running the normal fallback/outbox settlement. Treat these as incomplete recovery behavior and verify customer outcomes, rather than only updated status fields. Standard worker/delivery entrypoints also do not initialize the bounded structured logging configuration installed by the gateway/poller. Registry timeout/retry/scope metadata needs a clearly documented authority: current runner limits come from agent classes, and the planner is not reduced to the tenant's available catalogue.

The existing live decision report covers 60 synthetic classifier messages. It records useful results, including timeouts and missed human requests, but does not evaluate end-to-end tool authorization, semantic correctness, multi-turn completion or consistent performance across trials. The 33 golden cassettes test real persistence and graph control flow with predetermined model answers. Both forms of evidence are valuable and answer different questions.

For retrieval, create a labelled synthetic evaluation set in English, Malay/Manglish, Chinese and Tamil. Include conflicting policy versions, no-answer questions, long unbroken text, table/form questions and injected source instructions. Measure Recall@k/MRR or nDCG where applicable, grounded-claim precision, abstention, and false answers on unanswerable questions. Calibrate thresholds against that set rather than treating model-emitted capability scores or cosine similarity as probabilities of correctness. Identify an embedding space by model/revision and relevant preprocessing/prefix settings; the generic `tei-384` label alone cannot detect a changed server model with the same vector dimension.

**Recommended implementation direction.** Keep the current deployment units and package boundaries. Add a trusted, typed execution-authority object at ingress/staff/job adapters, with principal kind, tenant/contact ownership, allowed operations and execution mode. Models must not populate these authority fields. Check it in the runner and at sensitive service boundaries before every operation/retry. Maintain a separate final-egress policy for shadow, mute and review behavior. A sandbox channel check is a useful example of deterministic restriction, but the same principle must cover every principal.

Give each mutating task a durable operation receipt committed with its business change. Store the validated input digest and result necessary for safe replay. Use checkpoints to resume orchestration around these receipts, and test process failure after the business commit but before the checkpoint write. Align normal reply, failure reply and completion semantics so a deadline cannot select a second customer outcome.

The deferred [LG14 desktop-agent plan](/home/amsyrzmi/CSAV2/docs/langgraph-rebuild/LG14_teach_task_desktop_agent.md:13) proposes useful isolation, credential injection, tenant egress restrictions and administrator review. Before implementing it, define authority for each browser write, prevent credentials from entering recorded requests/screenshots/playbooks, and test final business state across changed layouts, expired sessions and retries. One successful recorded trajectory or dry run would not establish safe replay. Treat page content as untrusted input to the agent, consistent with the indirect-injection threat examined by [AgentDojo](https://arxiv.org/abs/2406.13352). This remains a design assessment; no desktop runner was exercised.

Preserve the transactional outbox and its existing unique message keys. Distinguish database deduplication from transport delivery: a provider can accept a send before the process records success. The current delivery process sends externally before committing delivery status and does not persist the returned Telegram message ID. Record channel receipts, define ambiguous-send handling, and document at-least-once external behavior where the provider supplies no idempotency facility. The [transactional outbox guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) explicitly discusses ordering and duplicate handling; the pattern alone does not establish exactly-once delivery.

Make an isolated image/Compose smoke test a release requirement. Build the actual application image, apply migrations to fresh disposable Postgres, supply temporary secrets through the same targets as deployment, start the three processes, exercise a synthetic customer turn and inspect its persisted result/outbox/receipt. Include shadow failure, indefinite mute, model-written callback, slow turn, same-key retry, and DLQ redrive scenarios. Preserve staged RLS without FORCE while the legacy owner-role dependency remains.

Before claiming broader readiness, add repeated live-model evaluations using separately authorized development credentials and synthetic data, plus a labelled adversarial corpus. This review did not make those calls. Measure complete-turn latency, model/embedding cost, queue age, delivery age, database/checkpoint load and error rates under a stated workload. Existing 50-request/s acknowledgement tests do not demonstrate 50 completed model-backed turns/s. There is no demonstrated need here to introduce Redis, Kafka, Kubernetes or a multi-agent swarm.
