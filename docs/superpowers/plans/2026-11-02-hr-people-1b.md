# People & HR project 1b (personal details, documents, leaving, assistant actions) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Profiles gain Personal details (with the new `sensitive_details` switch, encrypted and masked numbers, audited Show) and Documents; people can be marked as leaving, finished automatically the day after their last day, and rehired; the workspace dock can add, update and mark people as leaving through confirm cards and answer "who reports to" questions; the separate HR chat leaves the screen.

**Architecture:**
- **Database (migration `0521_hr_people_records.sql`):**
  - New tables `hr_employee_personal`, `hr_personal_reveals` and `hr_employee_documents`, all with no direct table grants: every read and write goes through SECURITY DEFINER functions.
  - New `hr_employees` columns for leaving. `hr_people_apply` is replaced to add `person.leave`, `person.leave_undo` and `person.rehire`. `hr_people_rows` is replaced to project the last day and leaving reason by viewer.
  - `hr_leavers_due()` and `hr_finish_leaver()` finish leavers; the main worker calls them every 15 minutes.
  - The `sensitive_details` switch is the grant row `("people.sensitive", "hr_operator", no fields)`.
  - `console_proposals_kind_check` gains `hr_person`.
- **Python:**
  - `csa/hr/personal.py`: personal-details contracts, masking, encryption and the service.
  - `csa/hr/documents.py`: upload, list, download and remove, with storage under `HR_UPLOAD_ROOT`, reusing the KB publish helpers.
  - Leaving and rehire are new operations on the existing `POST /console/v1/hr/operations` union.
  - `csa/workspace/hr_people.py`: the planner-side resolution of the new actions and the `HrPersonExecutor`.
- **Web:**
  - Personal and Documents profile sections; Mark as leaving, Undo and Rehire on the profile; status "Leaving"; My HR shows my personal details and my documents.
  - The dock renders the new `hr_person` card through the generic `ProposalCard`.
  - The HR chat `<details>` block on Home is removed.

**Tech Stack:** Python 3.12, FastAPI, pydantic v2, psycopg3, Postgres 16 (disposable containers), Next.js 16.3.8 app router, React 19, node:test.

**Spec:** `docs/superpowers/specs/2026-11-01-hr-people-design.md` (owner-approved 2026-11-01; amendment d70fd51 of 2026-11-02 adds the tax, EPF and SOCSO numbers). Scope is PR 1b only.

## Review Focus

1. **A retry after a lost response.** Saving personal details, uploading a document or marking someone as leaving with the same Idempotency-Key returns the first receipt, with no duplicate and no 409. The personal-save fingerprint is never a plain hash of an IC number, which could be guessed from a birth date: it is an HMAC with a key derived from `CREDENTIALS_KEY`. Pinned in Task 2, `test_personal_save_retry_returns_the_first_receipt_and_fingerprint_is_keyed`, and in Task 4, `test_document_upload_retry_with_same_key_stores_one_file`.
2. **Last day today.** Someone whose last day is today keeps their access all day. Their reports move today, and they are finished on the next Kuala Lumpur day. Two sweeps running at once, or the same sweep twice, finish them once. Pinned in Task 5, `test_finish_leaver_waits_for_the_day_after_and_runs_once`.
3. **A file that lies about its type** (a PNG or an .exe named `.pdf`, a ZIP that is not a DOCX, an empty file) is refused with `hr_document_type_unsupported`. A file name with quotes, Unicode or path characters is stored as given and downloaded with a safe `Content-Disposition`. Pinned in Task 4, `test_document_upload_checks_content_not_just_extension`.
4. **A personal value echoed in an error.** A 422 for a bad personal save (for example an IC with letters in the wrong place) returns `invalid_hr_input` without the submitted value. Pinned in Task 3, `test_personal_validation_error_does_not_echo_values`.
5. **Rehiring or leaving around a broken reporting line.** Rehiring someone whose old manager left keeps no manager. Choosing the leaver themselves, or one of their own reports, as the reports' new manager is refused with `hr_manager_loop`. Pinned in Task 5, `test_leave_refuses_new_manager_inside_the_leavers_tree` and `test_rehire_drops_an_inactive_manager`.

### Task 2: Personal details in the database

**Files:**
- Modify: `db/migrations/0521_hr_people_records.sql`
- Create: `db/sql/hr/personal_row.sql`, `personal_apply.sql`, `personal_reveal.sql`
- Test: `tests/test_hr_people_records.py`

**Interfaces:**
- **Table `public.hr_employee_personal`:**
  - key `(client_id, employee_id)`, with a FK to `hr_employees(client_id,id)`;
  - plain columns `date_of_birth date`, `home_address text`, `personal_phone text`, `emergency_name text`, `emergency_relationship text`, `emergency_phone text`, `bank_name text`;
  - encrypted `text` columns `ic_or_passport`, `bank_account`, `tax_number`, `epf_number`, `socso_number`;
  - bookkeeping `version integer NOT NULL DEFAULT 1`, `updated_at timestamptz`, `updated_by uuid`.
- **Table `public.hr_personal_reveals`:** `(client_id, id uuid, employee_id, field text CHECK in the five encrypted names, actor uuid, revealed_at timestamptz DEFAULT clock_timestamp())`. It is insert-only, with the `hr_immutable_record` trigger like `hr_employee_changes`.
- **`public.hr_personal_access(p_client uuid, p_employee uuid) RETURNS text`:**
  - `'hr'` for the HR owner or a `people.sensitive` holder (any employee of the tenant);
  - `'self'` when the caller's linked employee is `p_employee`;
  - otherwise NULL.
- **`public.hr_personal_row(p_client, p_employee)`:** returns `access text` plus every column above, including the ciphertexts. It returns no row when the access is NULL. Python masks.
- **`public.hr_personal_apply(p_client, p_key uuid, p_fingerprint text, p_body jsonb) RETURNS jsonb`:**
  - **Body:** `{"operation":"personal.save","employee_id","expected_version" (null when no row yet),"values":{plain fields},"encrypted":{column: ciphertext|null}}`.
  - **Encrypted values:** a key absent from `encrypted` keeps the stored value; `null` clears it.
  - **Self callers:** may only send the five self fields in `values` and an empty `encrypted`; anything else raises `hr_personal_field_refused`.
  - **Other refusals:**
    - `hr_personal_access_required` (42501) when access is NULL;
    - `hr_person_changed` for a stale version;
    - `hr_employee_unavailable` for an employee not in the tenant.
  - **Receipt:** writes the `hr_operations` row like `hr_people_apply`. A repeated `(p_key, p_fingerprint)` returns the stored receipt with `duplicate: true`, using the existing receipt lookup pattern in `hr_people_apply`/`HrOperations.apply`.
  - **History:** writes one `hr_employee_changes` row whose `changes` hold the changed field names with `{"old":null,"new":null}`. Encrypted fields are compared by "sent and different ciphertext, or cleared".
- **`public.hr_personal_reveal(p_client, p_employee, p_field text) RETURNS text`:** checks `hr_personal_access` is not NULL, inserts the reveal row, and returns the ciphertext (NULL when not stored).

  - **`PersonalSave(HrModel)`** in `automation_models.py`, added to the operations union:
    - `operation: Literal["personal.save"]`, `employee_id: UUID`, `expected_version: int | None`, `values: PersonalValues`;
    - `encrypted: dict[EncryptedField, SecretStr | None]` (default empty).
  - **Field rules:**
    - IC or passport: 5–20 characters of `[A-Z0-9-]`, uppercased;
    - bank account: 5–34 characters of `[0-9 -]`;
    - tax number: 5–20 characters of `[A-Z0-9 ]`;
    - EPF number: 5–20 digits;
    - SOCSO number: 5–20 characters of `[A-Z0-9-]`;
    - phones: the 1a work-phone pattern `[0-9+() -]{3,40}`;
    - address: ≤ 500; names: ≤ 120; relationship: ≤ 60; bank name: ≤ 100;
    - `date_of_birth` is not in the future.
  - **`HrPersonal(core: HrService)`:**
    - `get(session, employee_id) -> PersonalOut`;
    - `reveal(session, employee_id, field: EncryptedField) -> str | None`;
    - `save(session, body: PersonalSave, key: UUID) -> OperationReceipt`.
    - `save` encrypts in Python, computes the fingerprint as `hmac.new(subkey, canonical_json(body with SecretStr revealed), sha256).hexdigest()`, where `subkey = hmac.new(credentials_key_bytes(), b"hr-personal-fingerprint", sha256).digest()`, then calls `hr_personal_apply`.
    - `PersonalSave` is routed by `HrOperations.apply` to `HrPersonal.save` (refusals: `hr_personal_access_required` → `permission_denied`, `hr_personal_field_refused` → `personal_field_refused`, plus the existing `hr_person_changed` → `person_changed`).
  - **Routes:**
    - `GET /console/v1/hr/people/{employee_id}/personal` → `PersonalOut` (`Cache-Control: no-store`);
    - `POST /console/v1/hr/people/{employee_id}/personal/reveal` with body `{"field": EncryptedField}` → `{"value": str | None}` (`Cache-Control: no-store`; CSRF like the other HR writes).
  - **Profile sections:** `ProfileSection` gains `"personal"` and `"documents"`. `sections_for(viewer: Viewer, *, personal: bool, documents: bool) -> list[ProfileSection]` returns them in the order overview, personal, documents, access, history. `HrPeople.profile` passes `personal = hr_personal_access is not NULL` and `documents` from Task 4 (for now, `viewer == "hr" or personal == "self"`).

- **Error body:** the HR API's validation-error handler returns `{"detail":"invalid_hr_input"}` for HR routes, with no `input` or `ctx` echo. Check the existing handler and extend it if it echoes.
