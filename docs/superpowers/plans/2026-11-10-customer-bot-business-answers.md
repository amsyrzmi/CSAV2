# Customer Bot Business Answers and Escalation Ladder Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The customer bot answers, in English and Malay, what plans exist, which plan the customer is on and when it renews or ends, passes pause, cancel and change requests to staff, answers stock from our shop and TikTok Shop together with each source named, and hands off only after a ladder (two clarifying questions, a partial answer, then a handoff that carries a note for staff).

**Architecture:** Approach B of the spec. The subscription agent resolves the customer's own subscription from the chat's contact (`AgentContext.contact_id`, built from the envelope in `PostgresTurnDependencies.execute_spoke`), never from model output, and returns one worded fact per subscription or plan. Stock becomes one plannable `order_agent` action, `product_availability`, that reads the local catalogue and, when the company has Marketplaces, the TikTok listing reader, replacing `local_stock_first` and `tiktok_stock_fallback`. The ladder is deterministic code in `csa/graph/policy/plan_rules.py` on the existing `conversations.clarify_count`; the model only writes words. `compose_handoff` also writes a staff note and a gap topic; `finalize` stores the note on the escalation row (migration 0560) and the topic in `kb_gaps`; the inbox thread shows the note.

**Tech Stack:** Python 3.12, FastAPI, psycopg 3 async with SQL under `db/sql/`, PostgreSQL migrations with RLS, LangGraph graph in `csa/graph/`, Groq JSON calls in `csa/decide/llm.py`, golden cases (`tests/test_golden.py`, cassette model, real database), Next.js console with node tests.

**Spec:** `docs/superpowers/specs/2026-11-10-customer-bot-business-answers-design.md` (approved 2026-11-10, sections 8 and 9 binding). Also: `2026-11-10-business-surfaces-programme.md` (PR 2), `2026-11-10-customer-bot-conversation-design.md` (PR A, merged; this is its PR B), `2026-11-11-customer-onboarding-design.md` section 9 (`mine` includes `pending`, worded "waiting for payment").

## Global Constraints

- Migrations 0560 to 0569; this PR adds only `0560_escalation_note.sql`. Additive, no `FORCE` RLS. `EXPECTED_SCHEMA_VERSION` in `apps/gateway/main.py:71` goes from `"0550"` to `"0560"`; tests import the constant. Add the `0560`–`0569` line to `db/migrations/README.md` in the migration commit.
- A subscription is shown or requested only when `subscriptions.contact_id = AgentContext.contact_id` and `client_id = AgentContext.client_id`, in SQL, inside `tx(pool, client_id)`. A `subscription_id`, `current_plan` or `plan_code` from the planner only narrows within those rows.
- `mine` reads statuses `active`, `paused`, `pending`. The literal `'pending'` sits in the SQL allowlist today: the check `subscriptions_status_chk` (0480) refuses it, so no row matches until PR 2b adds the status; then it works with no change here. Requests act only on `active` and `paused` (the existing rule, `service.py:548`).
- A pause, cancel or change from a customer stays a draft for staff (`agent_preparation_requests`); the payload stores the resolved `subscription_id` and the target plan's code, as `executor.py:126-150` and `db/sql/subscriptions/request_get.sql` read them. The reply never says it is done.
- Only sellable products are described as available: TikTok `SELLABLE_PRODUCT_STATUSES` (`csa/marketplace/reads.py:67`), local `products.is_active`. No TikTok read on the web sandbox or without the `ecommerce_agent` capability. No write to TikTok.
- Ladder: unresolved counts 0 and 1 ask a clarifying question; 2 gives `partial_answer`; 3 or more hands off with reason `unresolved_turns`. `ask_clarifying` and `partial_answer` add one; chitchat and `ignore` keep the count; any other strategy resets it to 0. Wanting a person, anger, legal or police words, injection, a blocked message, voice failure and unsupported language skip the ladder (their routes already produce `escalate` plans).
- The staff note is never sent to the customer and never put in an inbox action receipt. The Telegram staff notification keeps carrying the reason only. Note at most 300 characters and two sentences, grounded in the conversation; column limit 500.
- Fact ids are constants (with an index suffix where there are several), never an order number, a subscription id or contact data.
- Exact copy, subscription facts (`csa/agents/staged/subscription_facts.py`; `{price}` is `money(price, currency)`, `{interval}` `month`/`year`, dates `day(value, ctx.timezone)` from `csa/agents/facts.py`, a `resume_at` date as `%d %b %Y`): plan `"{name}: {price} a {interval}."` plus `" Includes: {feature}; {feature}."` when it has features; active `"Your plan: {name}, {price} a {interval}. It renews on {date}."`; active with `cancel_at_period_end` `"Your plan: {name}, {price} a {interval}. ## Review Focus

- A customer with two live subscriptions says "cancel my plan": no request is prepared, the bot names both plans and asks which; the next "the Besar one" prepares exactly one request on that subscription (Task 4).
- Another contact's subscription id typed in the message or injected into the planner's input: the reply is the no-subscription sentence, no other plan name appears, no request row is written (Tasks 4, 7).
- A subscription set to cancel at period end: `mine` says "ends on" and never "renews"; a second cancel request says it is already ending and prepares nothing (Task 4).
- A product only on TikTok Shop is answered from TikTok, named as TikTok; with the live read failing, the stored listing is quoted with its age, or "can't check right now" when older than 6 hours (Task 5).
- A customer who says nothing new on the third unresolved turn gets a partial answer with one targeted question, not a third clarifying question; on the fourth the handoff carries a note; a request for a person on any rung hands off at once with `human_requested` (Tasks 6, 7).
- Malay: subscription and stock answers keep the casual register, dates and figures exactly as the facts write them, and "yes" to the handoff offer ("boleh", "ya") hands off (Task 7).
- Kill switches: with `conversation_memory` off the ladder still counts and hands off at rung 3; with `handoff_disabled` the rung-3 handoff is `unresolved_turns:disabled` and not required (Task 6).

## Deviations from the spec / survey corrections

- **Paths.** `plan_rules.py` and `routing.py` are `csa/graph/policy/` (`plan_rules.py:82-125`, `routing.py:46-85`), not `csa/decide/`. The ladder also changes `csa/turn/deps.py` (`finalize`, `deps.py:842-851`) and `csa/contracts/plan.py:46`.

- **`kb_gaps`.** The KB agent already records the planner's query, not the raw wording (`csa/agents/kb/agent.py:121-127`); dedupe is `md5(lower(query))` (`db/schema_baseline.sql:892`, `2029`). It stays; the handoff topic is added, so one question may leave two gap rows.

- **What happens next.** A staff decision on a request does not message the customer (`csa/subscriptions/service.py` `decide_request`), so the request fact promises no reply; what follows a handoff comes from the knowledge base (owner task).
- **Migrations.** Latest is 0550 (`db/migrations/0550_kb_job_cleanup.sql`), `EXPECTED_SCHEMA_VERSION = "0550"`. `escalations` has tenant RLS and `csa_app` UPDATE (`0150_escalations.sql:19-25`); 0560 also adds the `(client_id, conversation_id, created_at DESC)` index the inbox join and `recent_handoff.sql` use.
