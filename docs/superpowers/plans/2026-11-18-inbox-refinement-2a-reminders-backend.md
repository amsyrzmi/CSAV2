# Inbox refinement, part 2a: reminders and notifications backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Staff are reminded about Inbox work that waits: a generic reminder layer (`csa/reminders`) fires the six Inbox reminder kinds into a per-person console notification table and the company staff chat, the staff-chat messages are language aware, and the Inbox list can be filtered by who handles a chat.

**Architecture:** `csa/reminders` is a generic timer table plus a handler registry and a once-a-minute fire job; it knows nothing about conversations. `csa/notify/people.py` (`notify_people`) writes one `console_notifications` row per recipient and optionally a staff-chat notification through the existing `notify()`. Inbox registers six kinds in `csa/inbox_queue/reminders.py`. A sweep job schedules the reminders for items the SQL triggers put into the queue (Python has no hook there); handlers re-check the item when they fire, so a stale reminder is dropped. Recipients that the app role cannot read (the team, the tenant admins) come from SECURITY DEFINER functions, as HR's 0635 does.

**Tech Stack:** Python 3.12, FastAPI, psycopg 3 async, PostgreSQL migrations (`db/migrations`), pytest with testcontainers, import-linter, pyright, ruff.

**Spec:** `docs/superpowers/specs/2026-11-16-inbox-refinement-design.md`, sections 5.2, 5.3, 7, 8, 9, 10 (scenarios 3 to 6, 11 to 13, 17, 19, 20). The code survey this plan rests on is the "Decisions taken from the survey" section below. This is plan 2a; the screen part (bell, panel, deep link, Overview strip, navigation badge, Handled-by chip, Taken-over label) is plan 2b, written after 2a merges; the targets page and email are PR 3.

## Decisions taken from the survey (rulings; the spec stays the authority, these fill gaps)

1. **One scheduling mechanism for SQL-made entries: a sweep.** The 0622 triggers put customer-message and escalation items into `needs_staff` in SQL; Python never sees them. Instead of editing `inbox_queue_enter` (the ingestion hot path), a per-minute job `inbox_reminders_sweep` schedules what is missing. This is safe because a response target is at least 5 minutes (`target_*_min` range 5 to 10080), so the sweep always runs before an overdue time. It also covers the rollout (spec 7.3, "existing items at rollout"): an item in `needs_staff` with no `inbox.overdue` reminder for its cycle gets one due at `due_at` when that is in the future, else at `now + the response target for its priority` (the fresh clock; no burst).
2. **Sweep covers `inbox.overdue` (needs_staff), `inbox.stale_claim` (claimed needs_staff) and `inbox.snooze_due` (snoozed items with no reminder, i.e. those snoozed before this PR). Python schedules the rest in the same transaction as the transition:** `replied()` schedules `inbox.follow_up` and `inbox.handback` (the only way into `waiting_customer`), `snooze()` schedules `inbox.snooze_due`. Cost if wrong: chats already in `waiting_customer` at rollout get no follow-up or handback prompt (not required by the spec; noted in the PR).
3. **Cycle keys.** A reminder's `dedupe_key` is `<kind>:<conversation_id>:<cycle>` with cycle = `needs_staff_since` (overdue), `claimed_at` (stale_claim), `snoozed_until` (snooze_due), `last_staff_reply_at` (follow_up, handback), each as UTC epoch seconds. `schedule` is an upsert: on a conflicting key it updates `due_at` and `payload` only while `state='scheduled'` and `fire_count=0`. The sweep uses this to follow a priority change (`due_at` moves) without touching `set_priority`.
4. **Cancel is explicit and in the transition's transaction** (spec 7.3) as well as handler re-check: leaving `needs_staff` cancels `inbox.overdue` and `inbox.stale_claim`; reply, resolve, hand back and snooze cancel the item's pending kinds; release or reassign cancels `inbox.stale_claim`; a customer message that returns an item to the bot is handled by the handler re-check (it is SQL; the next fire drops it).
5. **Recipients.** The worker and the gateway app pool cannot read `console_users` or `console_memberships`. Migration 0624 adds two SECURITY DEFINER functions, `public.inbox_team_user_ids(p_client)` (enabled members with role `tenant_admin` or `tenant_staff`, account enabled, not read-only; every one who may use the Inbox) and `public.inbox_admin_user_ids(p_client)` (tenant admins), `EXECUTE` to `csa_app` only, each refusing a `p_client` other than `app.client_id` (the HR precedent: 0635 `hr_tasks_due`). A recipient who has left or been disabled is simply not returned; an assignee who is no longer returned by the team function makes the reminder fall back to the team.
6. **Fire job semantics.** `reminders_fire` is a per-client job with `own_transactions=True` (one transaction per row, as `payment_reminder_queue`): claim one due row `FOR UPDATE SKIP LOCKED`, run the handler inside a savepoint, write the decision, commit; a handler exception rolls back only that row's savepoint and reschedules it with backoff (`attempts`, `last_error`); the third failure marks the row `fired` with the error and stops. At most 500 rows per run per client. Two workers cannot double-fire (the job advisory lock plus `SKIP LOCKED`), and a crash after notifying replays safely because a notification's key is `<reminder id>:<fire number>` and both the console table and `notify()` are unique on it.
7. **Staff-chat events.** New event names: `inbox.overdue` only goes to the staff chat (spec 7.3); the other kinds are console only. Existing enabled targets get `inbox.overdue` appended by 0625 (`UPDATE ... WHERE is_enabled AND NOT 'inbox.overdue' = ANY(events)`); the column default is **not** changed (it is pinned exactly by `tests/test_bookings_bot_schema.py:39`; a newly connected chat opts in on the PR 3 page). Cost if wrong: a company that connects its chat after this PR gets no overdue alerts until PR 3 ships the page.
8. **Language.** The spec lists the target `language` column under 0625 in PR 3; this plan takes 0625 for it because the formatter changes now, so the **0625 here is "target language and the overdue opt-in"** and the per-person preferences of PR 3 move to **0626**. The spec's sections 7.2 and 9 get a one-line note. Console rows carry a message key and parameters; the browser renders them (console users have no language column), so only the staff chat renders text on the server (`en` default, `ms`).
9. **Platform admins** are not company members: they have no notification rows (list returns empty, count 0). A `read_only` member may read their own notifications and mark them read (the two routes join `_READER_POST_ROUTES`, `csa/console/access.py:33`, for the POST). The routes do not use the `customer_support` package gate, because HR kinds will arrive later.
10. **HR is untouched.** `csa/hr/reminders.py` `emit` keeps writing `hr_notifications`; HR forwards to this layer in its own change and then needs the (company, recipient, key) dedupe that `console_notifications` already enforces. `notify_people` takes already-resolved recipient ids so HR can pass its own.
11. **Handled by** is `handled_by=assistant|person` on the list route and in saved-view filters. "Person" means the existing computed flag `human_muted` (`owned_by='human_support'` and the mute not expired): the assistant is paused for this chat. A bot escalation also pauses the assistant for a day, so an unopened escalated chat counts as "person". The UI (2b) words it "Assistant paused". No migration. `inbox.handback` uses the same predicate at fire time.
12. **Wake and notify.** The `inbox_snooze_wake` job keeps waking items and its `{"woken_count": n}` result and `wake_snoozed` stay unchanged (tests pin them). The `inbox.snooze_due` handler is the notifier: at fire time, if the item is still `snoozed` and `snoozed_until` has passed it wakes it with a new `transitions.wake_one(conn, client_id, conversation_id)`; if the wake job already did, it sees a `woke` event at or after the reminder's due time. Either way it notifies once (the key protects a replay) and drops silently when the item has moved on.
13. **Scenario 3 deviation.** The spec's scenario 3 says the owner of a conversation "gets a console notification" when the customer writes again, but section 7.3 defines no kind for it, and the return to Needs us happens in a SQL trigger with no Python hook. This plan does not add an instant notification: the owner is reminded by the `inbox.overdue` reminder of the new clock (due after the response target). Cost if wrong: a person who owns a chat is not pinged the moment the customer replies (the Needs us tab and its count still show it). Adding it later is one more sweep query plus a kind.

## Review Focus

1. **Worker crash after notifying, and two workers in the same minute:** one console row and one chat message per recipient and fire, never two (scenario 20). (Tasks 2, 3, 5)
2. **One bad reminder must not stop the rest:** a handler that raises for one row leaves the others fired, backs off, and after three failures stops, never loops. (Task 2)
3. **Stale reminder:** the customer wrote, the item was resolved, snoozed, handed back, reassigned or its priority changed between scheduling and firing: nothing is sent for work that moved on; a priority change moves the due time. (Tasks 4, 5)
4. **Recipient no longer valid:** the assignee left the company, was disabled or is read-only: the reminder falls back to the team and does not raise; a company with no eligible recipient at all sends nothing and does not loop. (Tasks 3, 5)
5. **Rollout and scale:** old unhandled items get one fresh-clock reminder and no burst; the sweep is one indexed query per kind per company even with 50,000 conversations and 800 needing staff; the minute job never runs the sweep for a suspended or paused company. (Task 5)
