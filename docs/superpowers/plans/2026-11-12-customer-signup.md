# Customer Sign-up From the Chat (PR 2b-1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A customer asks to sign up in the chat, the bot collects name, phone and plan, reads them back and files one sign-up request on a typed "yes"; staff approve or decline it in a Sign-ups section (or a plan auto-approves it); an approved sign-up is a `pending` subscription that staff activate or that expires after 14 days.

**Architecture:** Approach B of the design. A new `signup_requests` table and service `csa/subscriptions/signup.py` (not the existing request queue). `SubscriptionAgent` gets one action, `request_signup`, whose confirmation is conversational (the planner sets `confirmed` only after a read-back, as the booking cancel does), so it works on Telegram and WhatsApp with no new buttons. `pending` is added to the status vocabulary everywhere it is enumerated. Cross-channel linking, Telegram "share my number", `merged_into` and verified phones are **PR 2b-2** (see Deviations).

**Tech Stack:** Python 3.12, FastAPI, psycopg 3 async with SQL under `db/sql/`, PostgreSQL migrations with RLS, Groq JSON calls in `csa/decide/llm.py`, golden cases (`tests/golden/`), Next.js console (`CSA_WebConsole/csa-console/web/`).

**Spec:** `docs/superpowers/specs/2026-11-11-customer-onboarding-design.md` (approved; sections 5 and 9 bind except where Deviations below overrides them). Also `2026-11-10-business-surfaces-programme.md` (PR 2b) and `2026-11-11-payments-design.md` (what activation will later wait on). The survey behind this plan is in the Deviations section; facts are as of main 2f4df4c.

- Pending row: `status='pending'`, `started_at` = approval time (column is NOT NULL), `renews_at` and `renewal_anchor` NULL, `price`/`currency` copied from the plan at approval, `version` 1. Activation (pending→active) sets `started_at` = activation time, `activated_at` = now, and `renews_at` and `renewal_anchor` with the SQL function `public.subscription_next_renewal(p_anchor, p_after, p_interval, p_tz)` (0481), exactly as `subscription_insert.sql` does; clients' timezone from `clients.timezone`. There is no table check `renews_at > started_at`; do not add one.
- `signup_requests(id uuid pk default gen_random_uuid(), client_id uuid not null references clients(id), contact_id uuid not null references contacts(id), plan_code text not null, full_name text not null (1..120), phone text not null (the number as the customer typed it, normalised by `normalise_my_phone`, never marked verified), status text not null default 'pending' check in ('pending','approved','declined','expired'), decided_via text null check in ('staff','auto'), decided_by uuid null references console_users(id), decline_reason text null (<=300), subscription_id uuid null, created_at timestamptz not null default now(), decided_at timestamptz null)`; unique partial index on `(client_id, contact_id, plan_code) WHERE status='pending'`; index `(client_id, status, created_at)`. RLS policy `tenant_isolation` and grants as `0541_training_library.sql` (`REVOKE ALL ... FROM PUBLIC, csa_ro, csa_identity; GRANT SELECT, INSERT, UPDATE, DELETE ... TO csa_app`). Tenant check: a trigger like `trg_preparation_contact_tenant` so `contact_id` must belong to `client_id`.
- `plans` gain `signup_mode text not null default 'staff' check in ('staff','auto')` and `is_signup_open boolean not null default true`; `subscriptions` gains `activated_at timestamptz null`. `subscription_settings(client_id uuid primary key references clients(id), pending_expiry_days integer not null default 14 check (pending_expiry_days between 0 and 90), version integer not null default 1)` with RLS as above; 0 means never expire; no row means 14 (`DEFAULT_SETTINGS`, as `csa/bookings/setup.py` does for bookings).
- A sign-up never charges, never activates a subscription by itself in this PR (staff do, until the payments PRs), never says approved before staff or the plan rule did. The reply to the customer says received and what happens next in one sentence, never "you are subscribed".
- A typed phone is stored only on the `signup_requests` row; on approval it is copied to `contacts.phone` only when that is empty. It is never a link key and never reveals another contact's data (no cross-contact lookup by phone anywhere in this PR).
- The customer is told once, in the asking turn, what is kept: "We keep your name and phone number on your contact record so the team can set up your plan." (fact `signup_data_note`).
- Capability gate: `subscription_agent` is seeded disabled and enabled by the `subscriptions` package; sign-up inherits it. One open request per (contact, plan): a second `request_signup` for the same plan returns the existing request (`ON CONFLICT DO NOTHING`, then read it). A contact with a live (`active|paused|pending`) subscription on that plan gets `signup_has_plan` and no request.
- Tenant isolation in SQL inside `tx(pool, client_id)`; every new SQL file under `db/sql/subscriptions/` or `db/sql/agents/`, named parameters.
- Staff routes: `/console/v1/subscriptions/signups...` declared before `/{subscription_id}`; same dependencies as the other routes (`human_session`, `package_gate("subscriptions")`, write roles platform_admin, tenant_admin, tenant_staff). Decline reason and request details are staff-only and never sent to the customer.
- Prompt rules are English with Malay examples; PR A's register block unchanged. Every task marked **[prompt]** runs `tests/test_golden.py` in full and `tests/test_llm_provider.py`, and the replay (`scripts/customer_bot_replay.py`) on staging after rollout.

## Review Focus

- A customer types a phone that is another customer's number: sign-up files with the typed number, nothing about the other contact is read, shown or linked (Task 4 test).
- The customer says "yes" to something that was not a read-back (a plain "ok" after a plans answer): no request is filed, the bot asks for what is missing (Task 4 golden + planner rule test).
- Two sign-ups for the same plan from one contact, and a sign-up for a plan the customer already has or has pending: one request at most, honest sentence, no duplicate row (Tasks 3 and 4).
- Staff approve a request whose plan was archived, closed, or repriced since: approval refuses with a clear 409 (`plan_not_open`) and leaves the request pending; a repriced plan uses the price at approval (Task 3).
- Two staff approve the same request at once, or staff approve while auto-approve ran: exactly one subscription (row lock on the request, status re-check) (Task 3).
- A pending subscription: shown to the customer as waiting, never "renews on"; staff cannot pause it; staff can cancel it now or activate it; an unpaid one expires after the company's days, 0 never (Tasks 2 and 5).
- Malay: asking, read-back and the "received" sentence keep the casual register; a bare "ya" confirms only right after a read-back (Task 4).

## Deviations from the spec / survey corrections

Rulings, each with what it costs if wrong:

1. **Split: this plan is 2b-1 (sign-up); linking is 2b-2.** The design's linking half cannot ship as written: after a link the Telegram ingress returns 409 on the next message (`_resolve_conversation` compares the conversation's contact to the resolved one; `resolve_telegram_contact.sql` needs the identity's contact to hold `telegram_id`), roughly thirty readers must follow `merged_into`, no phone normaliser or IMMUTABLE index function exists, the WhatsApp contact insert has no `ON CONFLICT`, the customer sees no "Link contacts" anchor in the console, and Telegram share-my-number needs a reply-keyboard in `Ui`, delivery, the parser and the persistence rule. *If wrong:* the owner wanted one PR; cost is a second plan, not rework. Migration range 0581–0589 stays reserved for 2b-2.
2. **Typed read-back and "yes" replaces the confirm button.** The design says "the existing confirm button (typed reply on WhatsApp)"; neither exists for this agent (`UiConfirmation.order_id` is required, WhatsApp ignores `ui`, pause/cancel requests have no customer confirm). The booking cancel already confirms by a typed yes (`booking.cancel_asked`, `confirmed true`), so the same works on both channels with no new transport. *If wrong:* a model that mistakes "ok" for a yes files an unwanted request; staff approval is the default and pending never charges.
3. **A typed phone is never trusted.** It lives on the request, is copied to `contacts.phone` only when empty, and is never a link key. `phone_verified_at` and the unique verified-phone index belong to 2b-2.
4. **Staff activate until payments exist.** The design activates on first payment; invoices exist but nothing creates subscription invoices, so P1 adds that. Here staff use a new `activate` action, and an auto-approve plan creates a pending subscription that staff still start (or it expires). *If wrong:* auto-approve saves less staff time than the design promised until P1.
5. **Archiving a plan stays unblocked.** `plan_in_use` runs only when the interval changes, so "pending blocks archiving" would also change archiving for active and paused subscriptions. Closing a plan to new sign-ups (`is_signup_open`) is the way to stop sign-ups; pending counts toward the interval-change block only.
6. **No staff push notification for a new sign-up in this PR.** The Sign-ups tab shows an open count; if filing a pause or cancel request notifies staff elsewhere, mirror it as a follow-up. *If wrong:* staff notice a sign-up later than they would with a push.
7. **Survey corrections to the design:** `renews_at > started_at` is a `WHERE` in `subscription_insert.sql`, not a table check; the portal "twin" is the same `SubscriptionsWorkspace`; PR 2's `mine` read already handles `pending`; there is no subscription settings table, so Task 1 creates `subscription_settings`; golden cases cannot send a callback tap or a contact share (hence no buttons here); the baseline `subscription_requests` table is unused and left alone.
