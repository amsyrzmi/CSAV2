## Decisions (rulings; the spec stays the authority, these fill what it leaves to the builder)

1. **One shell poll, two reads.** `useShellCounts` (in `components/console/shell/`, called once in `AppShell`) reads `GET /console/v1/notifications/count` (every company member, `read_only` included) and, only when the navigation holds an Inbox link (staff or admin with Customer Support active or suspended, the same gate as `canSeeInboxCount`), `GET /console/v1/inbox/queue/counts` for `needs_us`. 60 s interval skipped while the tab is hidden, a `focus` listener, an immediate re-read on every route change, `AbortController`, previous answer kept on failure, silent on error (copy `useActivePackages.ts`). **A platform admin gets no bell and no badge and makes no call**: they are not company members, the count route would answer 400 without a `client_id`, and the Inbox page already shows tabs with counts. Cost if wrong: a platform admin has no shell counts; they have none to show.
2. **Test stubs.** About 19 browser modules fail on any unknown browser-side `/console/v1` call (survey section 0.1). The shell polls are stubbed in every one of them through one shared helper `tests/shell_counts_stub.py` (`def shell_counts_answer(path: str) -> dict | None`: `{"unread": 0}` for `/console/v1/notifications/count`, a zeroed `QueueCounts` for `/console/v1/inbox/queue/counts`, else `None`) called first in each module's browser-side route handler; modules that already answer 404 "not stubbed" tolerate the silent poll and are left alone. Tests that assert the exact list of requests a page made (for instance `tests/test_overview_browser.py:589,743,959,973,986`) must ignore the shell polls: the helper module also exports `SHELL_COUNT_PATHS = ("/console/v1/notifications/count", "/console/v1/inbox/queue/counts")` and those assertions filter them out (a test of the poll itself, Task 2 step 1, asserts them explicitly). Where a module (the Inbox stub, Task 4) answers these routes itself, its own handler runs first and the shared helper stays the fallback.
3. **Bell and panel (design).** The bell sits between `ThemeControl` and `UserMenu` (`BAR_BUTTON` class, `Bell` icon 18 px, `data-testid="shell-notifications"`, count badge `shell-notifications-count`). The badge is the unread count, `99+` above 99, hidden at 0 or unknown, a 16 px round `--fs-primary` pill with `--fs-on-primary` text at the icon's top-right; it re-keys with the `fs-nudge` class when the count rises and motion is allowed. The panel (`POPOVER` class, 24 rem wide, `max-w-[calc(100vw-2rem)]`, `data-testid="shell-notifications-panel"`, `role="group"` named "Notifications") has a header row (title "Notifications" and the button "Mark all as read", disabled with 0 unread), a scrolling list (max-h 28 rem) of at most 50 rows and, when `unread` exceeds the rows shown, nothing else. A row has a title line (semibold when unread, normal weight when read), a detail line and a time line ("20 minutes ago", the absolute `companyDateTime` as its `title`); unread rows also carry the visible word "New" (a `StatusLabel`-style neutral label, never colour alone) and the sr-only text "Unread. " before the title. A row with a known link is a real link (`next/link`, `consoleHref(false, "inbox", { conversation })`) whose click marks that one row read (`POST /console/v1/notifications/read {ids:[id]}`) and navigates; a row with an unknown route is plain text that can still be marked read by a "Mark as read" button. Opening the panel does not mark anything read. The list is read on open and again when the polled count rises while the panel is open; it is never polled on its own. States: loading "Loading notifications…", empty "No notifications yet. Reminders about waiting customers appear here.", failed "Notifications did not load." with a "Try again" button, a failed mark-read restores the row and shows "Could not mark as read. Try again." in the panel; "Mark all as read" announces "All marked as read." in a `role="status"` line inside the panel. Optimistic update on mark-read with rollback. Cost if the owner dislikes the look: one component and its tests.
4. **Message text.** A pure renderer `renderNotification(item) -> { title, detail }` in `lib/notifications-view.ts`, English, never showing a key, id or UUID. Customer fallback "A customer" (capitalised: the name opens the detail sentence); durations as the staff chat writes them ("45 minutes", "1 hour 5 minutes", "2 days"). Titles and details: `inbox.overdue` "Waiting for your team" / "{customer} has waited {duration}." plus " Priority: high." or " Priority: urgent." for those two, plus " Reminder {repeat}." only when `repeat` is above 1; `inbox.snooze_due` "Snooze ended" / "{customer} is back in Needs us."; `inbox.stale_claim` "Claimed, no reply yet" / "{customer} was claimed but has had no reply. Waiting {duration}."; `inbox.follow_up` "Follow up or resolve" / "{customer} has not answered for {duration}. Follow up or resolve it."; `inbox.handback` "Hand it back?" / "{customer} has not answered for {duration}. You can hand the chat back to the assistant."; `inbox.assigned` "Assigned to you" / "{customer} was assigned to you."; any other key "New notification" / "Open the console to see the details." When `waited_minutes` is missing the sentences with a duration drop it ("{customer} is waiting for your team.", and so on, written in the tests). Params are all optional.
5. **Deep link.** The two inbox pages read `searchParams` (async, as `app/portal/payments/page.tsx` does) and pass `initialConversation` and, for the platform admin route, `initialClientId` to `InboxWorkspace`, which passes `initialConversation` to `Inbox`. `Inbox` selects it (`select(id)`: opens the thread, phone shows it) in an effect on the prop, accepting only a UUID-shaped value, and then drops the parameter with `router.replace` (path plus any other params), so the same link clicked again after Back changes the prop again. A conversation that is not in the loaded page or tab already opens through its detail read (`OpenConversation`); a 404 shows the thread's existing error. Tab and filters stay as they are. Platform admin: `InboxWorkspace` initialises its tenant from `initialClientId`, applied only on first render. Cost if wrong: the list does not highlight a linked row that is off the loaded page.
6. **Navigation badge.** `AppShell` passes `badges: Partial<Record<NavKey, number>>` (only `inbox`, from `needs_us`) to `Rail` and `TopBar` → `MobileMenu` as a separate prop, not a `NavLink` field (the contract test reads `navigation.ts` with a regex). Shown when above 0: `99+` cap, `aria-hidden`; the link's accessible name becomes "Customer inbox, N need your team" only then. Collapsed rail: the same number as a small pill at the icon's top-right (the label stays `sr-only`); mobile menu: right-aligned on the row.
7. **Overview strip.** Queue pills are appended from the same `inbox/conversations?limit=1` read the strip already makes (its answer carries `counts`): no new request. Order when counts are present: "Replies to check", "Needs us", "Overdue", "Mine", "Services on". `StripInput` gains optional `needsUs`, `overdue`, `mine`; a null or absent `counts` leaves them out (never zero); "Mine" is left out for a platform admin; "Overdue" takes the warning tone when above 0. Existing labels, test ids and the pinned strings (`tests/test_overview_browser.py:938,966`, which have no `counts`) do not change. New test ids `overview-strip-needs-us`, `overview-strip-overdue`, `overview-strip-mine`. Plain text, no links, no live region (the strip tests assert both).
8. **Handled by.** `QueueFilters.handledBy: "" | "assistant" | "person"`; query key `handled_by`; Filters popover group "Handled by" with radios "Anyone", "Assistant answering" (`assistant`) and "Assistant paused" (`person`, the owner's wording: the assistant is paused for that chat, by a takeover or by a bot escalation's one-day mute); chip labels "Assistant paused" and "Assistant answering"; saved views carry it (`filtersToView`/`viewToFilters` accept exactly those two values; today a view with `handled_by` is shown disabled). It is never a tab filter, so it is always a chip. Counts stay unfiltered (server rule).
9. **Taken over beyond Needs us.** In `rowMeta` the existing `reason` field is also set to "Taken over" (`REASON_LABELS.manual`) for a `waiting_customer` or `snoozed` item whose `human_muted` is true; never for `bot` or `resolved`; Needs us rows keep their own reason; no new `RowMeta` key (`tests/inbox-queue.test.mjs:785` pins five keys). The thread header is unchanged (it already says "Staff has taken over").
10. **Not in this plan:** an email path or per-person preferences (PR 3), a notifications page, a push or sound alert, a count in the browser tab title, notification kinds for HR, a window or virtual list in the panel (50 rows), live updating of the open panel beyond the rise rule, a Reopen action.

## Review Focus

1. **Poll storm and silent failure:** the shell makes one count call per minute per tab (two for Inbox staff), none while hidden, none for a platform admin; a 500, a 403 or a timeout leaves the old numbers and raises no page error. (Tasks 2, 3, 4)
2. **A notification for a conversation the reader cannot open or that no longer exists:** the row opens the Inbox with the thread's own "not found" state, never a crash or a blank page; a row with an unknown route or key renders as plain text. (Tasks 1, 4, 5)
3. **Same-route navigation:** clicking a bell row while already on the Inbox opens that thread; clicking the same row again after closing the thread opens it again; the phone shows the thread. (Task 5)
4. **Narrow screens and themes:** the bell and its panel at 320 px (no sideways scroll, panel inside the viewport), the badge in all three themes, the collapsed rail badge. (Tasks 3, 4)
5. **Unknown values:** an unknown filter value in a saved view, a count that is null or absent, a `message_key` this version does not know, `params` with missing or wrong-typed fields: nothing renders as "undefined", "NaN" or "0". (Tasks 1, 6, 7)
