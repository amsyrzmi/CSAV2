# CD pipeline, PR 3: GitHub setup script, auto-planned production runs, one runbook, one skill — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The GitHub side of both deploy targets is a repeatable, tested script (`deploy/github/setup-environments.sh`). The production plan can start by itself after a commit has been staged (repository variable `PROD_AUTO_PLAN`, default off), while the apply still waits for a person's approval on the `production` environment. One runbook (`deploy/DEPLOY.md`) and one skill (`deploy`) describe both targets. The stale "the owner approves the image publish" wording is gone.

**Architecture:** A new workflow `.github/workflows/deploy-production-auto.yml` starts on `workflow_run` of `deploy-staging` and has one job. It runs `deploy/production/auto_plan.sh` three times: `check` (is there anything to plan; the job ends green with a notice when not), `supersede` (cancel earlier auto-started runs whose apply is still `waiting`) and `start` (dispatch `deploy-production` with no input, then verify that a run appeared). `deploy-production.yml` and every script it uses stay byte-for-byte as they are. `deploy/github/setup-environments.sh` reads each environment, builds the complete desired state, writes only what differs and re-reads the environment after every write; it is tested against a stateful fake `gh` (`tests/fake_gh.py`) that models what was observed of GitHub's environments API (a PUT that either preserves or replaces what it omits, both undocumented, so the tests run under both; a 404 for the policy list of an environment with no custom policies). The real semantics were probed on a throwaway environment on 2026-11-18 (Part B keeps the probe as an optional re-check), and the script's re-read after every write is the permanent guard. `deploy/DEPLOY.md` becomes the entry runbook; whole generic sections move out of `deploy/PRODUCTION.md` and `deploy/STAGING_PIPELINE.md`, each leaving a heading and a pointer; a permanent test keeps the moved and stubbed headings in place, and a one-off builder check (not committed) proves no line of the old documents was dropped.

**Tech Stack:** bash, `gh` (REST API through `gh api`), `jq`, GitHub Actions, Python 3.12 + pytest (fake executables on `PATH`, structural workflow tests, doc assertions).

**Spec:** `docs/superpowers/specs/2026-11-13-cd-pipeline-design.md`, "Delivery" item 3, with the changes recorded below. Predecessors: `docs/superpowers/plans/2026-11-17-cd-pipeline-pr2.md` (merged; this plan follows its format and its Global Constraints).

## Plan decisions (mine; the owner may overrule)

Owner decisions already taken and **not open**: `PROD_AUTO_PLAN` defaults to off; the production apply always waits for a human approval on the `production` environment and is never approved by an agent; one runbook `deploy/DEPLOY.md` and one skill `deploy` replace the two skills; the setup scripts hold no real ids and are tested against fake executables on `PATH`.

1. **The auto-plan lives in its own workflow, not in `deploy-production.yml`.** The spec puts a second trigger in `deploy-production`. I deviate, for three reasons found by reading the real files:
   - **A waiting run holds the concurrency group.** `deploy-production.yml:31-33` uses the group `deploy-production`, and `deploy/PRODUCTION.md:129-133` already records that a run waiting for approval holds it: the next run queues as `pending` behind it. A gate job inside the new run would therefore never start while the very run it must cancel is waiting. GitHub's own text on concurrency: "At most one job or workflow run can be `pending` in the concurrency group" and `cancel-in-progress: true` cancels "any currently running job or workflow in the same concurrency group"; it says nothing about runs waiting for approval, and it has no way to cancel only a run whose apply is `waiting` and spare one whose apply is `in_progress` (a manual run in the middle of an apply would be cancelled too).
   - **Manual dispatch stays byte-for-byte.** Adding a trigger and a gate job to `deploy-production.yml` means changing the `if:` of its jobs and its `needs`. With a separate workflow, `git diff origin/main -- .github/workflows/deploy-production.yml deploy/production/{resolve_commit,ssm_run,parse_plan,deploy_entry,public_smoke}.sh` is empty, and Task 13 checks exactly that.
   - **Failure isolation.** A failing auto-plan is a red `deploy-production-auto` run, not a red staging run and not a red production run.

   The cost is one extra file and the fact that GitHub starts the plan by a `workflow_dispatch` made with the workflow's own `GITHUB_TOKEN` (`actions: write`). GitHub documents that `workflow_dispatch` and `repository_dispatch` events always create runs when made with `GITHUB_TOKEN` ("events triggered by the `GITHUB_TOKEN` will not create a new workflow run," with those two exceptions). I considered a final job inside `deploy-staging.yml` that dispatches after `record` succeeds (it would need no "nothing to plan" pre-check for the paused, `already staged` and `superseded` outcomes, because those runs have no `record`). I rejected it: it adds a `actions: write` job to the workflow that holds the staging OIDC role, and a failure there would turn a successful staging run red.
2. **The `workflow_run` chain is within GitHub's limit, and the dispatch is not part of it.** GitHub: "You can't use `workflow_run` to chain together more than three levels of workflows"; in its example A → B → C → D → E → F, "workflows `E` and `F` will not be run" (docs, "Events that trigger workflows", `workflow_run`). Here ci (A) → publish-staging-images (B) → deploy-staging (C) → deploy-production-auto (D) is three `workflow_run` links, the last allowed. The dispatched `deploy-production` is a `workflow_dispatch` run, not a `workflow_run` link; the docs do not say whether it counts, so Part C proves it, and `auto_plan.sh start` fails red (not silently) when no run appears after the dispatch. (The literal spec design, a `workflow_run` into `deploy-production` itself, would be a fourth link, also allowed.)
3. **`workflow_run` semantics, cited.** For a `workflow_run` event GitHub's table gives `GITHUB_SHA` "Last commit on default branch" and `GITHUB_REF` "Default branch", so `github.ref == 'refs/heads/main'` holds only while `main` is the default branch (`deploy-staging.yml` relies on the same). `branches:` "specif[ies] what branches the triggering workflow must run on". The page does not define `head_branch`; the repository's own PR 2 finding (2026-11-17) is that `workflow_run.head_sha` is not the commit the run handled. So the workflow reads **no** field of `github.event.workflow_run` in a `run:` text, only `conclusion`, `head_branch` and `head_repository.full_name` in the job `if`, exactly as `deploy-staging.yml:68`, and it plans the **tip of `main`**, never an event sha.
4. **No red noise: a `check` step decides, the conclusion of the staging run does not.** `deploy-staging` ends `success` for `paused`, `nothing to roll out`, `already staged` and `superseded` as well as for a real rollout, so `conclusion == success` proves nothing. `auto_plan.sh check` asks the facts: it runs `resolve_commit.sh` with `DEPLOY_TARGET=staging` (`deploy/production/resolve_commit.sh:56`, `:150-155`: staging never refuses at the staged check and reports `staged_on`, empty when the tip has no record; exit 3 means not ready, `:116` and `:193`). The resolver's `production` target is **not** used, because its not-staged refusal exits 1 and would be a red run. `check` ends green with a notice when:
   - the tip's ci is not green or its images are not published (resolver exit 3): `nothing to plan: <resolver message>`;
   - the tip has no staged record (staging paused, superseded, or the record job failed): `nothing to plan: main's tip <sha7> is not staged yet`;
   - a `deploy-production` run for the tip already exists that is queued, in progress, waiting or concluded `success`: `a deploy-production run for <sha7> already exists: <run id>`. A run that failed or was cancelled does not block, so an owner's early manual dispatch that failed with "not staged yet" does not stop the auto-plan;
   - any other resolver failure is red (exit 1): it is a real problem.
5. **Cancelling stale waiting runs: what GitHub can and cannot do.**
   - It cannot do it by concurrency (decision 1). The only mechanism is the REST call `POST /repos/{r}/actions/runs/{id}/cancel`, which needs `actions: write` and which cancels a run whatever its jobs are doing; it is not atomic with "the apply is still waiting". The endpoint answers 202 or 409 (the docs are silent on 409): a 409 is treated as "not cancelled": the script reports it, re-reads the run once and does **not** retry in a loop.
   - `supersede` therefore cancels only a run for which **all** of these hold, read just before the call: run status `waiting`; event `workflow_dispatch`; `triggering_actor.login` is `github-actions[bot]` (the auto-plan's own dispatches; a person's manual run, a rollback with an explicit `sha`, is never touched); `head_branch` `main`; `head_sha` differs from the tip being planned (a run for the same commit is the dedupe rule of decision 4); its jobs are exactly `plan` (completed, success) and `apply` (status `waiting`), none `in_progress` or `queued`. A run whose apply is `in_progress` is **never knowingly** cancelled (see the race below).
   - **Fail closed on every field.** Before any comparison `.head_sha` must be a 40-hex string, and `.event`, `.head_branch` and `.triggering_actor.login` must be strings; otherwise the run is left alone (`unreadable fields`). This matters because in `jq` `null != $sha` is true, and `triggering_actor` is `null` for a deleted account. A named test proves it (Task 6).
   - **The race is narrow, not absent, and its outcome is benign.** The rule is a read followed by a POST, not an atomic step: on PR 2's live run a run read `waiting` was `in_progress` one call later, after the owner approved it. A window of one API round trip therefore remains in which an approval can land before the cancel. In that case the apply's first steps are `Require the deploy variables` and `Check the commit is still current` (`deploy-production.yml:145-183`), both before the AWS credentials step (`:190`). A late cancel then hits a run that is about to fail that check, or one that would deploy only the commit the approver saw in the plan. Precisely: a dispatch run's `head_sha` is the tip of `main` at **dispatch** time, while the plan's sha is resolved later in the plan job. If `main` moved in between, a run whose `head_sha` differs from the tip may have planned the tip itself; a race-approved stale run then passes the tip check and deploys the tip, a commit its approver saw in the plan (benign, but not "older than the tip"). For a run that planned an older sha the check fails (`main moved to <sha7> since this run's plan`). The duplicate guard is keyed on `head_sha`, so it can miss a run that planned the same sha: harmless, the stale run is cancelled and the replacement starts. `deploy/production/ssm_run.sh` has no cancel trap (its only trap removes a temporary file), so a cancel that arrives after the SSM command was sent does not stop that command on the instance.
   - A cancel that fails is re-checked: when the run is no longer `waiting` it is left alone and the line says so; when it is still waiting, the line says so and the step continues (the new run queues behind it, as today, and the owner rejects the stale one).
   - **Accepted limit, documented in DEPLOY.md.** (a) `supersede` runs once, before `start`: an earlier auto run whose `plan` job is still `in_progress` is not listed as `waiting`, so it is missed; the new run queues behind it and the owner rejects the older one. (b) The concurrency group is shared with manual runs (`deploy-production`, at most one pending): if a manual run waits and a second manual run is pending, an auto dispatch becomes the pending run and the pending manual run is cancelled by GitHub's own rule. `supersede` never cancels a manual run, but this concurrency rule can replace a person's *pending* (not waiting) run. I accept this: it is rare, the switch is off by default, and the owner can dispatch again.
   - GitHub has already notified both reviewers about each waiting apply; cancelling does not recall that. This is why the default is off.
   - The `triggering_actor` marker is the part I cannot verify by reading: GitHub documents the event but not the actor shown for a token-made dispatch. Part B proves it (step 7 captures it while the run waits; step 8 re-reads it) and the constant (`AUTO_ACTOR` in the script) is the one line to change. Failing safe: if the marker never matches, nothing is cancelled. Likewise the job-level status of an apply awaiting approval is **not observed** (the docs list `waiting` for jobs; only the run-level `waiting` is verified): Part B step 7 captures it; if the job reads `queued`, `supersede` never cancels (fails dead, not unsafe).
6. **Security reasoning: the auto path cannot skip the approval.** The apply approval is a property of the `production` **environment** (required reviewers; main-only branch policy), not of the workflow file, so no workflow change can remove it. The auto workflow has no `environment`, no `id-token` permission and no secret; its token can read the repository, read Actions and deployments and write Actions (cancel and dispatch). Approving a pending deployment (`POST .../pending_deployments`) needs a user who is a required reviewer; the token is not one, and the script and workflow contain no call to it (a test asserts that). The workflow dispatches with no `sha` input, so it can never request an explicit rollback. It never checks out or runs anything from the triggering run (`ref: main`; no artifact download; no event field in run text), which is the usual defence for `workflow_run` workflows. `PROD_AUTO_PLAN != 'true'` makes every job skip (the run concludes `skipped`).
7. **Setup script: read, build the whole desired state, write only on difference, then verify.** What is known about `PUT repos/<r>/environments/<env>`: GitHub's published body is `wait_timer`, `prevent_self_review`, `reviewers` and `deployment_branch_policy`. `can_admins_bypass` is not in the published description, but a probe on a throwaway environment on 2026-11-18 showed that the PUT **accepts** it and that the GET reads it back. The same probe showed that a PUT carrying only `deployment_branch_policy` did **not** reset reviewers, `prevent_self_review` or `can_admins_bypass` that an earlier full PUT had set (an earlier hand run on 2026-11-17 had been read as replace-on-PUT; the controlled probe did not reproduce it). Neither behaviour is documented, so the plan does not rely on either: `apply` does `GET`, builds the complete body from the current values plus the desired changes, sends the `PUT` only when something differs, and **re-GETs the environment after every PUT**, failing loudly (exit 1; counts and names only, no secret) when reviewers, `wait_timer`, `prevent_self_review` or `can_admins_bypass` differ from what was intended. The fake `gh` can be set to either semantics (merge, the observed default; replace, the pessimistic reading), and the script's tests run under both: they prove the script is correct whichever way GitHub behaves, not which way it behaves.
   - `reviewers`: the given `--reviewer` set when any was given, otherwise the current reviewers (`.protection_rules[] | select(.type == "required_reviewers") | .reviewers[] | {type, id: .reviewer.id}`); `wait_timer` and `prevent_self_review` are carried over (a new environment gets 0 and `false`; the owner's decision is one approval with self-review allowed, so `false` is the wanted value, and the script never changes it). `can_admins_bypass` is `false` for `production` and `production-plan` (the owner's decision, applied to the real repository on 2026-11-18; the script now treats `false` as the wanted value there, a `true` is an announced change `admin bypass: true -> false (changed)` and `--check` reports it as `differs`); for `staging` and `staging-images` it is carried over (a new one gets GitHub's `true`), and no parameter changes it. `deployment_branch_policy` is `{protected_branches: false, custom_branch_policies: true}`.
   - **How production's reviewers are preserved:** by that carry-over; `production` is refused (after reading every environment of the target, before the first PUT) when it has no reviewer and none was given, so the script can never leave it unprotected. **Extra guard:** on an **existing** `production`, when the wanted reviewer set differs from the live one, `apply` prints the old and the new logins and refuses unless `--replace-reviewers` is also given; `--check` shows the difference first. A test with a pre-existing production environment holding two reviewers, `wait_timer` 5 and `prevent_self_review` true proves that `apply` with no `--reviewer` sends a body that still holds them.
   - The custom branch policy is **a separate `POST`** of `{"name":"main","type":"branch"}` to `.../deployment-branch-policies`, made after the `PUT` and only when `main` is missing; any other policy is `DELETE`d after `main` exists. An environment with custom policies on and none listed admits nothing, so this order is fail-safe. **A real environment whose `deployment_branch_policy` is `null` answers 404 `Not Found` (exit 1) to both the list and the POST** (GitHub docs, branch policies; `staging-images` is in this state today). So "policy missing" for such an environment is derived from the environment's own GET without listing, and `apply` lists and POSTs only after the PUT that turns custom policies on (or when the GET already says they are on). The same OpenAPI description lists 303, not 422, for a POST of a pattern that already exists; the script never POSTs a duplicate (it lists first) and treats any POST failure as a failed step.
   - Reviewers on `staging`, `staging-images` and `production-plan` are **preserved and reported**, never added or removed by the script (a reviewer on `staging` is rejected in PR 2's decisions; on `staging-images` it would hold every merge, so `check` prints it as a note, not a failure).
8. **`staging-images` gets the main-only policy.** Read-only check on 2026-11-18: `staging-images` has `protection_rules: []` and `deployment_branch_policy: null`: no reviewer (as the spec says) **and no branch restriction either** (the spec and `deploy/RELEASE.md:112-115` describe `main`-only). A workflow on any branch could use it and its `packages: write`. `setup-environments.sh staging` adds the `main` policy to it: one PUT that turns custom policies on (the environment has no reviewer and no wait timer, so there is nothing to lose), then the POST. `publish-staging-images` runs on `main` in every real case (`workflow_run` runs on the default branch; dispatch is made from `main`), so the policy does not stop it; Part C watches the first publish after the change.
9. **Secrets: environment variables or hidden prompt, never argv, never printed.** Names, by environment (read from the two deploy workflows, `grep -rnoE '(secrets|vars)\.[A-Za-z_]+' .github/workflows` on 2026-11-18, plus the existing runbook step):

   | Environment | Reviewers | Secrets | 
   | --- | --- | --- |
   | `staging` | none | `STAGING_DEPLOY_ROLE_ARN`, `STAGING_INSTANCE_ID` |
   | `staging-images` | none | none |
   | `production-plan` | none | `PROD_PLAN_ROLE_ARN`, `PROD_INSTANCE_ID` |
   | `production` | the given set (required) | `PROD_APPLY_ROLE_ARN`, `PROD_INSTANCE_ID`, `PROD_CONSOLE_ORIGIN` |

   Repository variables: `IMAGE_NAMESPACE` (both targets), `STAGING_DEPLOY_REGION` (staging), `PROD_DEPLOY_REGION` (production); the switches `STAGING_AUTO_PAUSED` (staging, set only with `--paused`) and `PROD_AUTO_PLAN` (production, set only with `--auto-plan`; unset means off). `GITLEAKS_LICENSE` (ci) and `GITHUB_TOKEN` are out of scope. A secret value comes from `SETUP_<NAME>` in the environment, or a hidden `read -rs` prompt on a terminal, and reaches `gh secret set` on **stdin** only. A secret that already exists is never overwritten unless its `SETUP_<NAME>` is set (explicit rotation), so a routine run prompts for nothing. Secrets cannot be read back, so `check` reports `set` or `missing` by name, from the documented list `gh api --paginate "repos/<repo>/environments/<env>/secrets?per_page=100"`; variables are read with `--paginate` too. The admin check is `gh api repos/<repo>` (`.permissions.admin`), **not** `gh auth status`, which exits non-zero when any other configured account is stale. Values are validated (ARN, node id, origin) before any write, and no message ever contains a value. Variable values are never printed either, except the two on/off switches, whose whole content is `true` or `false`.
10. **Whole sections move; a permanent test keeps what must stay, a one-off check proves nothing was dropped.** The two old docs are large and their text is asserted by tests. I move **whole level-2 or level-3 sections verbatim** (then adjust wording) and leave the heading in the old file with a one-paragraph pointer when a test, a code message or another doc points at it. The permanent test (Task 9) covers only what is stable: the `MOVED` headings exist at their destination and the `KEEP_STUB` headings still exist in the old file with their pointer line. It does **not** freeze all 84 headings, because every later legitimate heading edit (the feature-rollout sections are edited with each feature) would then fail it. Completeness is proved once, by a one-off, uncommitted builder check in Tasks 10 and 11: every non-blank line of the old `PRODUCTION.md` and `STAGING_PIPELINE.md` appears in the new three-document set or is on an explicit "intentionally edited" list (headings alone do not prove no sentence was dropped). Host-specific procedures stay where they are (install steps, secret files, restore, pruning, feature rollouts, reset, the manual break-glass commands); cross-cutting explanation moves (the pipeline, outcomes, failures, rollback meaning, setup order). A few rules, such as the staged rule, are stated in both places on purpose.
11. **Publish pins.** `publish-staging-images.yml` pins its two third-party actions (`actions/checkout`, `actions/download-artifact`, both `@v4`) to the commit each `v4` tag points at today, with a `# vX.Y.Z` comment, in a separate small task. I do not jump to the `v7` checkout the deploy workflows use: this workflow publishes the images, and an unproven major upgrade is a different change. The controller resolves the commits read-only (Task 8). `ci.yml` has many more unpinned actions (`docker/*`, `astral-sh/setup-uv`, `gitleaks/gitleaks-action`, `actions/*`): out of scope, listed below.
12. **Stale wording is replaced by one sentence in every place, verbatim:** "The image publish needs no approval today (the `staging-images` environment has no reviewer). If a reviewer is added to `staging-images`, every merge waits on that click." Every test needle for it is a fragment of this one sentence (`no approval today`, `the `staging-images` environment has no reviewer`, `If a reviewer is added to `staging-images`, every merge waits on that click`), matched case-sensitively exactly as written here; where a document needs a different grammatical shape it still contains the second sentence verbatim. ## Global Constraints

- The repository is public. No hostname, address, account id, managed-node id, ARN, bucket or real region goes in any file, test, commit or PR text. Stand-ins: `mi-0123456789abcdef0`, `zz-test-1` (matches the region pattern and the no-real-region scan), `repo:example-owner@1001/CSAV2@2002`, an ARN with an invented twelve-digit account id (tests only, never in docs: the doc scan forbids twelve-digit ids), `example-owner/CSAV2` as the test repository, logins `reviewer-a` and `reviewer-b`. Docs and Part B name the real repository `amsyrzmi/CSAV2` literally, as PR 2 did. The two existing reviewer logins appear only where the current `PRODUCTION.md` already names them and in the moved "Deploying from GitHub" paragraph that now lives in `DEPLOY.md` (a move, not a new mention); the plan, the new scripts, the tests and the new `DEPLOY.md` sections use the placeholders `<login-1>` and `<login-2>`. No agent-session temporary or scratch path and no session id appears in any file, this plan included (the PR 2 doc tests scan owned docs for such strings, and Task 12 adds this plan to that scan): the test wrapper is called "the controller's wrapper (path given by the controller)". Never read secrets, `/srv/csa-staging/secrets` or anything under `/srv/csa-prod`.
- No secret reaches a log, argv, the job summary or the repository. Values reach `gh` on stdin only; `set -x` and `eval` do not appear; the setup script prints no value (tests plant marker values and grep every output stream and the fake's call log).
- Every `uses:` is pinned to a 40-hex commit with a `# vX.Y.Z` comment. The new workflow uses `actions/checkout` at the same pin as `deploy-production.yml` (`actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`) and no other action.
- Workflows run only from `main`: every job has `if: github.ref == 'refs/heads/main'`, scripts come from `actions/checkout` with `ref: main`, `persist-credentials: false`. Values reach scripts through `env:`, never through `${{ }}` in run text.
- Shell strictness for every new script: `#!/bin/bash` first line, `set -euo pipefail`, then `export LC_ALL=C` **before** any `=~` (regex ranges follow the locale), a `valid <pattern> <value>` helper that also refuses a newline, `jq` for every JSON read and write, no `eval`, no `sh -c`, no `source`, no `set -x`, every `$` expansion inside double quotes. The repository's quote checker `_unquoted_expansions` (`tests/test_production_deploy_assets.py:1493`) is asserted over every new script: write the script so it passes line by line (a `$(...)` that spans a line is fine; an unquoted `$x` is not). Every input is validated before the first `gh` call.
- `deploy-production.yml` and `deploy/production/{resolve_commit,ssm_run,parse_plan,deploy_entry,public_smoke}.sh` are **not modified**. Task 13 verifies the empty diff.
- Test helper reuse across files, explicit: `tests/fake_gh.py` (new, Task 1) is imported by `tests/test_github_setup_environments.py` and `tests/test_production_auto_plan.py`; the workflow tests import `PIN`, `ROOT`, `_children`, `_jobs`, `_steps`, `_step`, `_run_blocks`, `_run_step`, `_unquoted_expansions`, `_workflow` from `tests.test_production_deploy_assets` (their `path` parameters already default to the production file, `tests/test_production_deploy_assets.py:1871-1905`, `:1931`). # As built

Where the code differs from the plan above (the plan itself is unchanged):

- **The auto workflow's concurrency group** is the shared `deploy-production-auto` group only when the staging run succeeded, ran on `main` (`head_branch == 'main'`) and came from this repository (`head_repository.full_name == github.repository`), and `PROD_AUTO_PLAN` is `true`. Any other run gets its own idle group. The plan names only the conclusion and the switch.
- **The fake `gh` state key** that makes a dispatch create no run is `dispatch_no_run`, not the environment variable `FAKE_GH_DISPATCH_NO_RUN` the plan names.
- **Task 4 fixes** (commit "setup-environments.sh never traces or exports a secret; prompt names its target; stronger guards"): tracing is switched off before any `SETUP_<NAME>` is read, every such name that is a valid shell identifier is moved out of the environment before a child process starts, and the prompt names the environments the value will be set on.
- **The agent never cancels a production run.** The plan's `deploy` skill text says "cancel only after the owner's go". As built, the skill says an agent never cancels a production run itself: it reads the state and hands the owner the exact `gh run cancel` command, and the only automatic cancel is the workflow's `supersede` under its conditions.
- **The Trust paragraph** no longer says the staging trust model rests on required review: the repository ruleset `main: pull requests only` requires a pull request, no bypass and no force push or deletion, but no approving review and no status check. `deploy/DEPLOY.md` records the owner's command, the check and the removal under "Protect main".
- **End-of-branch review items** added after the plan: letter case ignored in the switch comparison; the empty `SETUP_` name is dropped; the start wait rounds up; the red "no run started" message ends with "look for a run before starting another"; a hung staging apply has its own outcome row; `setup-environments.sh` prints `rotated` for an overwritten secret and `changed` for an overwritten `--region` or `--image-namespace` variable; `scripts/staging_reset.py` says "all five services".
