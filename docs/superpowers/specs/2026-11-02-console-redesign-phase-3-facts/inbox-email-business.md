Common mechanics (apply to all three screens)
- `api()` in `W/lib/api.ts`: non-2xx becomes `ApiError(status, message, code, body)`. `message` = a friendly sentence only if the server `detail` code is in the `explained` map (api.ts:16-100), otherwise the RAW server `detail` string is shown to the user. ### B. Data
Server endpoints (all under `/console/v1/inbox`, router in `csa/console/inbox.py`; every call needs the tenant: tenant members implicit, platform admin must pass `client_id=<uuid>`, else 400 "platform admin must select client_id explicitly"):
- `GET /inbox/conversations` (`inbox.py:317`). Query: `before` (uuid cursor), `limit` (1-50, default 20; the UI never sends it so it is 20), `channel` (`telegram|whatsapp`), `needs_review` (bool), `sender` (`known|new`), `q` (max 64 chars; under 2 chars -> 422 "search needs at least two characters"). Response: `{items[], next_cursor, needs_review_count}`; `needs_review_count` ignores every filter and counts live (unexpired) pending replies per conversation for the whole tenant. Item: `id, channel, status, owned_by, ai_muted_until, human_muted, inbox_version, opened_at, contact{display_name, telegram_username, phone_masked, phone(null in list), kind, known}, last_message{preview, at}, pending_approvals`.
  - Order: last activity (last message time, else opened_at) newest first. Excludes console sandbox chats and staff chat participants. Only channels telegram and whatsapp.
- `GET /inbox/conversations/{id}` (`:358`): same shape with the FULL phone; used for `inbox_version` (needed for writes). Polled every 3 s while a conversation is open (`OpenConversation.tsx:13-33`).
- `GET /inbox/conversations/{id}/messages` (`:367`): `before` (uuid), `limit` 1-100 default 50. Newest first; UI reverses. Message: `id, direction, author, body (redacted, 8000 max), created_at, trace_id, delivery_status, delivery_error, provider_status, provider_error`. Polled every 3 s (`usePages.ts`).
- `GET /inbox/approvals` (`:390`): `conversation_id`, `include_handled` (bool), `before` (int), `limit` 1-50. Item: `id, conversation_id, trace_id, draft, reason, status, expires_at`. Statuses seen in UI code: pending, approved, edited, rejected, expired (anything else shows "Handled"). The thread polls pending only; the card polls handled history only while the checkbox is on.
- Polling: `usePages` re-fetches every 3 s (`usePages.ts:79`), and with N "Load older" pages it re-fetches ALL N pages each tick. `useTicker` (30 s) only refreshes relative times. Failed refresh keeps old rows and shows a banner.
- Overview's `StatusStrip.tsx:65` also calls `GET /inbox/conversations?limit=1` for the "needs review" number.

Server-side filters that EXIST: channel, needs-review, sender known/new, free-text search (name, @username, phone in local/international form), cursor paging, and a tenant-wide needs-review count.
Server-side filters that DO NOT exist: date or date range, conversation `status` (open/escalated is returned but not filterable or shown), owner (assistant vs staff), unread/unanswered, assigned-to, sort order, total count, sender text search inside message bodies. -> A date-range or "owned by" filter or "unanswered" filter **needs backend change** (new query params in `inbox.py` and `db/sql/inbox/list_conversations.sql`; index work may follow - migration 0501 already added list indexes). Client-side filtering is NOT honest here: only the loaded pages (20 per page, cursor) are in memory.

Write endpoints (`inbox.py`):
- `POST /inbox/conversations/{id}/takeover`, `/release` (body `{request_key: uuid, expected_version: int}`), `/reply` (adds `body` 1-2000; 202). `POST /inbox/approvals/{id}/decide` (`{request_key, decision: approve|reject|edit, text?}`).
- Errors: 409 "conversation changed; refresh before acting" (stale version), 409 "take over the conversation before replying", 409 "This conversation has no active channel to reply on.", 422 edit text errors, 404 "customer conversation not found" / "reply approval not found", 413 body > 32 KB. Same `request_key` replays the stored result (idempotent); same key with different content is 409 "request key was used with different content".
- Shared proposals (Approve/Reject): `POST /console/v1/workspace/proposals` kind `inbox_decision`, then confirm/cancel on the card (`workspace-api.ts` createProposal/confirmProposal/cancelProposal).

### C. Actions, role gates, irreversibles
- Who: `platform_admin`, `tenant_admin`, `tenant_staff` for everything (`inbox_actor`, `inbox.py:147`). `read_only` gets 403 "staff inbox permission required" and the page shows "Staff inbox access requires..." (nav hides the tab for them anyway).

- Reply to customer: "Queue reply" - NO confirmation; the message is inserted and a delivery is queued at once (irreversible once delivered; WhatsApp 24-hour window can reject it later). A redesign should add an explicit "Send reply" confirm or at least clear wording; today the only guard is the take-over step.
- Approve / Reject a held reply: goes through the shared proposal card with explicit Confirm / Cancel (keep this). Approve sends the assistant's drafted reply to the customer (irreversible).
- Edit a held reply: browser confirm "Queue this edited reply for delivery?", then direct POST (no proposal card).
- Uncertain failures keep the request key and offer "Retry the same action"; this must be preserved (double-send protection).
- Every mutation is audited (`inbox.takeover|release|reply|reply_decided`).

## Cross-cutting findings for the design
1. The Customer inbox is the only one of the three with true server filters (channel, needs-review, known/new sender, search). It has no date filter; adding one needs a backend change.
2. Email has no server-side filtering, paging or search at all (query string is locked to `client_id`); it loads <=200 threads and <=100 drafts in one go, so client-side chips (unread, category, priority, draft status, received date) are honest if labelled "last 90 days, up to 200 emails".
3. Business management cannot support honest date-range + status chips with the current API: needs backend change (status, payment_status, date range, search, per-status counts, and a `(client_id, created_at)` index), and the front-end hook must accumulate pages instead of replacing them.
4. Unmapped server codes appear raw in notices on all three screens (api.ts `explained` map); a friendly-copy pass needs entries in `W/lib/api.ts` (shared) and email sentences in `lib/email-recipients.ts`.
5. Irreversible actions that must stay behind explicit confirmation: inbox Approve (shared ProposalCard), inbox Edit (browser confirm) and Queue reply (currently NO confirm), email Send (dialog + version check), email Save to Gmail drafts (ProposalCard). Currently unconfirmed destructive-ish actions worth gating: email Delete draft, Disconnect Gmail, Switch off for tenant, inbox Take over.
6. Two components carry extremely heavy wording-coupled tests: inbox (`test_inbox_redesign_browser.py`, `test_packaged_console.py` inbox section) and business (`identity-transport.test.mjs` source assertions); email is covered by one browser test with exact call counts.
