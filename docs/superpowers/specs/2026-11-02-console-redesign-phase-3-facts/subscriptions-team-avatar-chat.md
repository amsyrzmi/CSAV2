### How the 11 are produced
- Source art: `ui-guide/assets/agents/<id>.svg` (body-only, viewBox `-8 -8 176 176`, transparent, gradient + clip path + shade + eyes), copied to `W/public/fourstacks/agents/<id>.svg` (the copy the generator reads). Six (support, knowledge, orders, tickets, ecommerce, invoices) are exports of the FourStacks landing-page profiles via `ui-guide/scripts/export-avatars.mjs`; five (assistant, hr, email, subscriptions, bookings) come from profile objects in `ui-guide/scripts/draft-new-avatars.mjs` (silhouette path, spectrum 3 stops, shade, accent, eyes, tendrils, marking). `ui-guide/assets/agents/manifest.json` lists each (id, title, silhouette, eyeCount, colors, `artKind` null for the new five, `working` null) and `ui-guide/AGENT_AVATARS.md` has the identity table and palette table.
- Generator: `scripts/pixelate_avatars.py` (1115 lines; `python -m scripts.pixelate_avatars`, `--check` fails if `lib/pixel-avatars-data.ts` differs). Steps: (1) Playwright Chromium draws each SVG at 16x onto a canvas for grid 32 and 48 (`rasterise`, :117); (2) each cell takes the most frequent palette entry among 256 samples (nearest colour to the SVG's own hex colours; alpha < 140 = transparent); (3) `drop_orphans`; (4) `recolour` moves every non-outline, non-white colour to the agent's hue (`HUE` table :44, `SOURCE_HUE` 215, `HUE_SPREAD` 0.35, saturation x1.05), merges duplicates, at most 12 palette entries; (5) `idle_frames(agent, grid, palette)` (:253) builds 4 frames per grid from per-agent motion helpers (shift/shear/scale/region_shift/blink); (6) `working_frames` (:755) builds 8 frames on the 48 grid only from `working_plan` (:776) plus hand-drawn prop stamps in `PROPS` (:402; letters `.owhmd` = transparent / outline / white / lightest / main / darkest tone; at most about 14x15 cells, email trays 19x5); (7) `render` writes the RLE data module.
- Data format `lib/pixel-avatars-data.ts` (114,653 bytes; test caps at 150 KB, so a 12th avatar at about 10 KB fits): `PIXEL_DATA[id] = { palette: ["#RRGGBB", ...≤12], idle: {"32": [4 frames], "48": [4 frames]}, working: {"48": [8 frames]} }`. A frame = 32 or 48 rows joined by `/`, each row RLE tokens `<symbol><count>` (`.` transparent, `a`..`l` = palette index 0..11). Frame 0 of idle is the rest pose (also the still frame, reduced motion, offscreen); working frame 7 must be within 2 px of rest (wake hand-over). `#15203A` (outline) and `#FFFFFF` (eyes) are in every palette.
- Decode/draw: `lib/pixel-avatars.ts` (`decodeFrame`, `frameRects`, `avatarPlan`, `gridForSize`: sizes 32/64 use grid 32, 48/96/144 use grid 48, working/wake only on 48 and fall back to idle on 32), `components/console/fs/AgentAvatar.tsx` (SVG of `<rect>` runs, CSS keyframes in `app/globals.css:379-423`).

### Can the generator run without Chromium for a hand-drawn sprite?
- As written: no. `generate()` always calls `rasterise()` (launches Playwright Chromium) for ALL ids and `--check` too; `python -m scripts.pixelate_avatars` needs `playwright==1.64.0` with a browser installed (pyproject.toml:91). Host is memory-constrained; CI/staging has it.
- But the pure-Python half needs no browser: `drop_orphans`, `idle_frames`, `working_frames`, `build_agent(agent, sources)`, `encode_frame`, `render` are all importable (tests/test_pixelate_avatars.py already runs them with no Chromium). `build_agent` takes `sources = {32: (palette_hex_list, grid), 48: (palette_hex_list, grid)}` where grid is a 32x32 / 48x48 list of palette indices (-1 transparent). So a hand-drawn sprite can be fed in as those two grids (same source palette on both sizes, ≤ 12 colours after recolour, containing `#15203A` and `#FFFFFF`), then `render()` plus the existing 11 entries (parse them back with the `load()` regex in tests/test_pixelate_avatars.py, or keep the old text) gives the new data module. The `idle_frames`/`working_plan`/`PROPS` code for the new id must still be written (motion + prop are code, not data).
- Caveat: `--check` (CI-able but local-heavy) would then compare a Chromium rasterisation of the SVG against the committed data, so the committed SVG must rasterise to the same grids. Options: (a) make the SVG from one `<rect>` per cell at the 48 grid (exact at 48, nearest-vote at 32, compare with `--check` after one real run), or (b) add a `HAND_DRAWN` branch in `rasterise` that returns the hand grids for that id and skips the SVG vote (a small change to the generator and then `--check` is stable). Either way one real Chromium run in CI/another host is needed to prove `--check`.

### Which avatars lose contrast on night if the tile were removed
Method: rest pose (idle frame 0, 48 grid); counted the silhouette's exposed edge cells (non-transparent cells 4-adjacent to transparent) whose colour is under 3:1 against `#141E33` (3:1 is the non-text bar the repo's theme-contrast test uses).
- Finding 1: the navy outline is NOT the silhouette edge (0 of about 130 edge cells for 10 of 11 avatars; knowledge has 19); it is the eye wells and markings (3 to 8% of cells). On night those internal outlines go to about 1.03:1 against the page but they sit INSIDE the body, so they still read against the body fill and the white eyes stay 16.6:1. The silhouette edge is the body colour itself, which is why body-tone contrast matters.
- Finding 2 (edge cells under 3:1 on night surface): support 71 of 158 (45%), hr 49 of 125 (39%), assistant 33 of 108 (31%), orders 36 of 150 (24%), invoices 23 of 140 (16%), bookings 11 of 129 (9%), email 6 of 138 (4%); knowledge, tickets, ecommerce, subscriptions 0. Cause: each sprite's darkest shade tone (lower right shade overlay): #1431A9 1.62, #1F3FCE 2.11, #7A1848 1.62, #A21E5E 2.28, #7E26C3 2.34, #99148D 2.25, #9D2418 2.14, #925716 2.85, #166B9E 2.87.
- Judgement: would clearly lose their lower-right edge on night: **support, hr, assistant** (deep blue/crimson/violet), then **orders, invoices** (brown, mid-blue), marginal **bookings, email**. Fine without a tile: knowledge, tickets, ecommerce, subscriptions (all tones ≥ 3.7:1).
- Conditions: on cobalt and bureau the tile is only about 1.1:1 off the surface (`#eaf0ff` on `#ffffff`, `#efe7d6` on `#fffdf8`), so removing it changes almost nothing there (and the pale yellow/lime/mint bodies already sit low against light surfaces, which the existing test comment accepts). Only night changes: today the night tile `#dbe6fb` is a bright square that is 12.9:1 above the outline and carries every sprite; removing it makes night the one theme where dark shades fall into the page.
- Options if the tile goes: keep a night-only subtle tile (`--fs-sprite-tile` maps to surface-blue or a ring), add a light 1px edge pass in the generator for night, or lighten the shade tones in the generator. Any of them touches the three token tests above.
- The 12th avatar: new sprite should avoid shades under 3:1 on night; hue gaps left (existing hues 5, 28, 50, 95, 145, 172, 200, 225, 268, 305, 330): the largest free arcs are about 95-145 (centre 120), 50-95 (centre 72) and 225-268 (centre 246), each still only about 21 to 25 degrees from a neighbour, so shape and prop must carry the identity (e.g. document/stamp motif).

### Behaviours that must be preserved
- Statuses and honesty wording: `queued | processing | held | awaiting_delivery | available | failed | no_reply` map one-to-one to `sandboxStatus` (server states, `lib/sandbox-chat.ts:15`); "held" must not read as delivered; `failed` must say not to assume a reply or action; 90 s delay notice (`sandboxDelayed`, exactly > 90 000 ms for queued, processing, awaiting_delivery only) with "do not send again yet".
- Retained request keys: every text turn has `request_key = crypto.randomUUID()` and the same key is reused on retry; the pending draft (`pending`) keeps key and body; `observed` set of keys seen in the poll clears `pending` and says "This message is already in the chat, so you do not need to send it again."; 4xx (not 408) restores the text and says "We could not send your message: …"; 5xx/timeout leaves `pending` and says "We cannot tell whether it was sent. … it will not be delivered twice."; button becomes "Send the same message again" (`retry={pending?.source === "text"}`).
- Creation key: `creationKey` ref survives a failed "New chat" (`createFailed`, label "Try creating the chat again"); first Send with no thread creates the chat then sends; the draft stays; "Trying again repeats the same request, so no second chat is created."; switching conversation clears a failed creation notice but keeps the key.
- Uncertain voice: `VoiceConversation` keeps `pending.current` {key, blob, body} across stop/error, "Resume same request", "Discard local recovery" (then the typed draft returns), the Send button and history selection stay disabled while a voice request is pending/running; `onPending` pushes `{source:"voice"}` so polling does not unlock it; transcription job endpoints are idempotent per key (`POST/GET /chat/conversations/{id}/voice/{key}`); mic released on stop (`window.voiceTest.microphones === 0` in the test); next question while a reply is spoken interrupts playback.
- Recorded voice: 8 MB / 60 s limits, consent checkbox, uncertain state "Check status / retry same recording" with same key, transcript goes to the composer for review (never auto-sent).
- Read-only role: `canWrite = role !== null && role !== "read_only"`; read-only can read chats, chips/send/new chat/archive/dictate disabled, notice shown.
- Scroll behaviour (`scrollPlan`): follow bottom for first load, own question, or reader at bottom; keep offset when "Older messages" adds above; never pull a reader away on poll.
- Focus: refocus the textarea after a send if focus was in the composer; Enter does not send while composing (IME); mobile Enter = newline.
- Polling 2.5 s per thread with `AbortSignal.timeout(15 s)`, `historyPages` paging with "Older messages"; poll failure shows "We lost touch with the chat…" without blocking the composer; the full disclaimer shows when the first read fails (`!loaded`, tests `test_disclaimer_shows_when_the_first_read_fails`).
- Archive: confirm text, disabled while locked/read-only; server keeps nothing deleted.
- `speechSynthesis.cancel()` and dictation stop on unmount and on thread switch; "Stop reading aloud" must stay reachable.
- Tenant handling: platform admin needs `?client_id=`; the chat is keyed by tenant (`<Sandbox key={tenant}>`) and every API path adds `client_id` for platform.
